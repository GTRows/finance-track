<objective>
Ship Track F1 + the per-asset delta broadcast item from CONCERNS.md as the FIRST plan of Phase 30 "Performance & Polish". The work has two coupled concerns: (a) audit the hot read paths for query-count regressions (`buildPortfolios` on the dashboard, `sumNetWorth` in FIRE, `listForUser` on bills, `listForPortfolio` on dividends, `buildUpcomingBills` on the dashboard) where service-layer loops issue a child-table query per parent row, and replace those loops with a single batched repository call (`findByPortfolioIdIn`, `findByBillIdInAndPeriod`, `findByAssetIdIn`) followed by an in-memory grouping pass — keeping JPA's existing FK-by-UUID idiom (we do NOT introduce `@ManyToOne` associations or `@EntityGraph`/`JOIN FETCH` because no such associations exist in the codebase today; every entity stores foreign keys as raw `UUID` columns and resolves them via repository lookups, which is the convention 24-08 / 25-02 / 27-* / 28-* / 29-* all extend); (b) refactor `PriceBroadcaster.broadcastAll()` so it tracks the previous tick's prices in an in-memory map keyed by `assetId` and emits only the assets whose `(price, priceUsd)` actually changed since the last tick, with a small relative tolerance to suppress spurious last-decimal wiggle.

Purpose: Phase 30's roadmap line ("N+1 audit + index pass + virtualized lists") closes its first of three sub-plans with this work. Today the dashboard fires 1 + N portfolio-holdings queries plus 1 + N bill-payment lookups when the operator opens `/`, FIRE recomputes the same N portfolio-holdings query when it derives net worth, and the WebSocket pushes the entire ~80-asset master list every 30 seconds even when only one or two prices changed. Concretely after this plan: opening `/dashboard` issues a constant number of queries regardless of how many portfolios or bills the operator has; opening `/portfolios/{id}/dividends` issues two queries (the dividend list + a single batched asset fetch); the price broadcaster typically pushes 1-3 prices per tick instead of 80; a Hibernate `Statistics`-backed `@DataJpaTest` integration test pins the query-count contract so future regressions surface in CI rather than in production.

The WebSocket delta refactor changes the broadcaster from a stateless "read all + push all" component to a stateful one that holds a `ConcurrentHashMap<UUID, PriceSnapshot>` keyed by `Asset.id`. On each `broadcastAll()` invocation: read every priced asset, diff against the previous-tick snapshot, build a `PriceUpdate` for every asset that is new, removed, or whose `(price, priceUsd)` moved by `> 0.0001` relative to the prior value (tolerance documented; 0.01% threshold suppresses last-decimal float noise without dropping real moves; a separate "force-full-broadcast" path is used on first tick after startup so a freshly-connected client always receives a snapshot of the current state). Constraining decisions:
- **No `@EntityGraph` / `JOIN FETCH`.** The codebase stores foreign keys as raw `UUID` columns and resolves them via repository lookups (the only `@ManyToOne` association anywhere is `PriceAlert.asset`, which is not on a hot read path). `@EntityGraph` and `LEFT JOIN FETCH` only help when a parent entity has a lazy `@OneToMany` / `@ManyToOne` association; that is not the case here. The fix is "issue ONE batched query and group in Java", which is the same shape `DashboardService.buildPortfolios` already uses for assets. The plan name carries "@EntityGraph" from the roadmap; the executor MAY introduce a single `@ManyToOne` association if Task 1 surfaces a strong reason — the default plan does NOT, because doing so changes the entity contract and risks breaking existing JSON projections + repository tests across 23-01's 39 `@DataJpaTest` files. Documented in "Decisions Made".
- **No `findAll`-style change.** The unbounded `findAll` flagged in CONCERNS.md (audit log, alert, asset) is out of scope. F2 (the index pass + pagination) is the next sub-plan (30-02); the executor flags any worsening of those reads as a CONCERN-bump in the SUMMARY.
- **No async broadcast.** The broadcaster runs synchronously on the price-scheduler thread today and continues to do so after the refactor. Moving the broadcast to a separate executor would add ordering hazards (an older delta arriving after a newer one) and is unnecessary at single-user scale.
- **Snapshot memory.** The in-memory `lastSnapshot` map is bounded by the asset master size (~80 entries today, ~200 cap per the cache config). Memory cost: 200 × (UUID + 2 × BigDecimal + Instant) ≈ 30 KB. Documented in JavaDoc.
- **First-tick semantics.** A reconnecting client that subscribes mid-session receives the next delta (which may be empty and produce no frame). The cold-boot full broadcast only runs once per JVM. A future enhancement (out of scope here) is a "snapshot on subscribe" mechanism via STOMP message replay; the current behaviour is acceptable because the React Query layer separately invalidates `['portfolios']` + `['dashboard']` on every tick, which forces a REST-side refetch that re-syncs the price view from the DB. Documented in "Deferred Enhancements".
- **Tolerance choice.** `0.0001` (0.01%) is large enough to swallow last-decimal `setScale(4, HALF_UP)` rounding noise and small enough to never miss a real move. Smaller would re-broadcast cosmetic noise; larger would miss real moves on stable-coin pairs. The threshold is hard-coded; it does NOT become a configurable property because runtime tuning is unnecessary and a config knob expands the surface area without a use case. Documented in "Decisions Made".
- **Removal not broadcast.** When an asset disappears from the priced set (e.g., admin un-imports it — currently impossible), the broadcaster does NOT emit a removal event. The frontend's price store keeps the stale value until the next reconnect. Documented in "Deferred Enhancements" + "Decisions Made".
- **No service-level cache invalidation change.** The new batched repository calls hit the same DB rows as the per-row calls; existing `@CacheEvict` boundaries on `PriceSyncService.persistUpdates` and the analytics caches (25-02 / 29-01 / 29-02 / 29-03) stay unchanged.
- **Test isolation.** `QueryCountRegressionTest` runs as a `@DataJpaTest` slice; it does NOT load the full Spring context (so `DashboardService` is not auto-wired). The regression test exercises the BATCHED REPOSITORY method directly + asserts the count cap. Service-layer "did the loop go away?" is verified separately via Mockito in `DashboardServiceTest` / `BillServiceTest` / `FireServiceTest` / `DividendServiceTest`. This split keeps the slice fast and does not bring in the Caffeine cache / OTel pipeline at test time.
- **Rollback boundary.** `git revert` of this plan's commits is sufficient — no Flyway migration, no schema change, no dep addition. Frontend revert restores `applyBatch` semantics; the frontend tolerates the older 3-field envelope shape after revert. Backend revert restores the per-row queries; the dashboard slows back down but stays correct. Match the 29-* / 28-* precedent of describing the trivial rollback in the SUMMARY.
