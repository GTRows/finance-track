Constraining decisions:
- **Threshold is fixed at 1000.** Not measured at runtime, not configurable per consumer beyond the `threshold` prop override (which exists ONLY for tests + future call sites with different scale assumptions). Documented in the JSDoc.
- **Row markup ownership stays at the call site.** The primitive does NOT bake in `<div role="row">` styling; it wraps `renderRow(item, index)` in `<div role="row" key={getItemKey(item)} style={{ ... virtualizer position ... }}>` and the call site's returned ReactNode is its only child. This keeps the primitive thin (under ~120 LoC) and avoids prop-drilling Tailwind tokens.
- **Header rendering lives on the primitive's `renderHeader?` prop.** The header is NOT virtualized (it's a single row at the top); the primitive emits `<div role="rowgroup">` containing the header above the virtualized body's `<div role="rowgroup">`. Both rowgroups inside an outer `role="table"` ancestor when the call site wants table semantics.
- **No window-level scrolling.** The primitive owns its own scroll container with `style={{ height: '70vh', overflow: 'auto' }}` (default; override via `className`). Window-level virtualizers (`useWindowVirtualizer`) are NOT used because the existing layouts wrap the lists in `<Card><CardContent>` boxes that own their own bounding box.
- **Selection state stays in `BudgetPage`.** The primitive does NOT own selection. `BudgetPage`'s existing `selected: Set<string>` Zustand-flavored local state continues to drive the per-row checkmark; the row component reads `selected.has(txn.id)` via its `selected` prop and emits the toggle callback up.
- **Investment-transaction edit flow stays unchanged.** `TransactionLog.tsx` does NOT currently expose an "edit" affordance (only delete + record-new); the migration preserves the same surface. The ROADMAP wording "edit, delete, hover, sort, filter, multi-select" enumerates the FULL spectrum of preserve-on-virtualization concerns; not every concern applies to every consumer (the investment transaction log doesn't have multi-select or sort today). The plan preserves whichever interactions exist on each consumer; it does NOT add new interactions.
- **No CSS-driven `scrollbar-width: thin` change.** The existing scrollbar styling is project-wide; the virtualizer's scroll container inherits.
- **Cold-boot first-render correctness.** Under React 18 strict mode, the primitive is mounted twice in development. `useVirtualizer` handles this transparently — no special handling needed.
- **No SSR concerns.** The app is a SPA (Vite); `@tanstack/react-virtual` is SSR-safe but the consideration does not apply here.
