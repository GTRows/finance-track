Ship Track F2 as the SECOND plan of Phase 30 "Performance & Polish": a `pg_stat_statements` EXPLAIN pass plus the missing-index Flyway migration that the 30-01 query-shape audit and the existing repository method names imply. Three coupled deliverables:

1. **Static query-plan inspection (proxy for live `EXPLAIN ANALYZE`).** A real `pg_stat_statements`-driven `EXPLAIN (ANALYZE, BUFFERS)` walk against a populated production-shaped database is not reachable from a planning step; the plan documents the proxy approach: derive the likely-slow query set from the JPQL/native queries shipped in repositories (V1..V46), reason about their execution plans assuming the existing index inventory, and add indexes for the obvious gaps. The list of inspected queries plus the plan-time assumed plan + the chosen index decision is captured per-index in the migration's SQL comments.

2. **Missing-index Flyway migration `V47__index_audit_phase30.sql`.** Postgres does NOT auto-index foreign-key columns; FK columns participating in repository lookups OR in `ON DELETE CASCADE`/`ON DELETE SET NULL` rules pay scan cost on every parent delete. The 30-01 inspection already enumerated four hot read paths; 30-02 broadens that to the full FK + ORDER BY surface. The migration adds the following indexes (each motivated, named, and grouped — full list with rationale below):
   - `idx_holdings_asset_id` on `portfolio_holdings(asset_id)` — covers `HoldingRepository.findByPortfolioIdAndAssetId` AND the `ON DELETE` reverse-scan when an asset is removed; today the V1 schema only declares `UNIQUE(portfolio_id, asset_id)` which Postgres uses as a composite index whose leading column is `portfolio_id` — `asset_id`-only lookups force a sequential scan.
   - `idx_inv_txns_account_id` already shipped in V42 as a partial; `idx_bill_payments_account_id` ditto. NO new account-id index needed.
   - `idx_alert_notifications_alert_id` on `alert_notifications(alert_id)` — covers the `ON DELETE CASCADE` reverse scan when a `price_alert` is deleted; today the V9 schema indexes `(user_id, created_at DESC)` and `(user_id) WHERE read_at IS NULL` but never `alert_id` standalone.
   - `idx_price_alerts_asset_id` on `price_alerts(asset_id)` — `ON DELETE CASCADE` reverse scan; V9 indexes `(user_id)` and `(status)` but never `asset_id`.
   - `idx_alert_notifications_asset_id` on `alert_notifications(asset_id)` — same rationale.
   - `idx_savings_goals_linked_portfolio_id` on `savings_goals(linked_portfolio_id) WHERE linked_portfolio_id IS NOT NULL` — covers the `ON DELETE SET NULL` reverse scan when a portfolio is deleted; partial because `linked_portfolio_id` is nullable and the live row count where it is NOT NULL is small.
   - `idx_dividends_asset_id` already exists as a composite `(asset_id, payment_date DESC)` (V34); the leading-column rule covers `asset_id`-only scans. SKIP.
   - `idx_recurring_templates_category_id` on `recurring_templates(category_id) WHERE category_id IS NOT NULL` — `category_id` is nullable + unindexed; partial.
   - `idx_allocation_buckets_category_id` on `allocation_buckets(category_id) WHERE category_id IS NOT NULL` — same rationale.
   - `idx_transaction_tags_transaction_id` SKIP — V24 declares `PRIMARY KEY (transaction_id, tag_id)` whose leading column is `transaction_id`, fully covering the FK reverse scan.
   - `idx_bill_payments_period` already exists (V1) — KEEP. Hot ORDER BY columns: `transactions.txn_date` (V1 + V28 composite), `bills.due_day` (covered by `findByUserIdAndActiveTrueOrderByDueDayAsc`'s scan over the small bills set per user — sequential is fine at single-user scale; SKIP), `audit_log.created_at` (V12), `bill_payments.period` (V1), `dividends.payment_date` (V34 composite).
   - `idx_bill_payments_bill_period` on `bill_payments(bill_id, period)` — composite tightening the existing `idx_bill_payments_bill` + `UNIQUE(bill_id, period)`. The `UNIQUE(bill_id, period)` index already provides the equivalent leading-column lookup; SKIP. Document the SKIP and the reason inline so the next reader doesn't re-add it.
   - `idx_inv_txns_asset_id` already exists (V1, line 89). KEEP.
   - `idx_assets_asset_type` on `assets(asset_type)` — `AssetRepository.findByAssetTypeOrderBySymbolAsc` filters by `asset_type`. Asset master is ~80-200 rows; sequential scan is cheap. SKIP and document.
   - `idx_authenticators_credential_id` on `authenticators(credential_id)` IF the column exists in V38. Inspect V38 in Task 1; add if missing.

   The full set of indexes in `V47` is finalized at Task 1 inspection time; the seed list above is the planner's working hypothesis. Each index that actually ships carries a SQL comment: query-path served + selectivity reasoning + write-cost note.

Constraining decisions:
- **No backfill required.** All V47 indexes are `CREATE INDEX` (NOT `CREATE INDEX CONCURRENTLY` — Flyway transactional migrations cannot use `CONCURRENTLY`). At single-user homelab scale the table sizes are small (`portfolio_holdings` ≤ ~200 rows, `alert_notifications` ≤ ~thousands, `recurring_templates` ≤ ~dozens, `savings_goals` ≤ ~tens), so the `CREATE INDEX` table lock is sub-second. Document in the migration header. If the index pass were ever to be re-run on a multi-tenant deployment, switching to `CONCURRENTLY` would require splitting V47 into one index per migration file and removing the implicit Flyway transaction; that is a future scaling concern, not a v1 issue.
- **No statistics extension.** `pg_stat_statements` is opt-in via the monitoring overlay; the live database does NOT load it. The plan does NOT modify the live `docker-compose.yml` to set `shared_preload_libraries`.
- **No dropping of existing indexes.** The audit only ADDS coverage; it does not consolidate. A future "index consolidation" pass (merging redundant indexes — e.g., dropping `idx_bills_user` if the migrations confirm `bills` is only ever read by `(user_id, due_day)`) is its own plan.
- **No application-side query rewrites.** 30-01 already refactored the N+1 hot paths; 30-02 only addresses the index inventory. Any query that EXPLAIN reveals as costly is documented in the SUMMARY for a future plan to handle, not silently rewritten here.
- **Snapshot of the index decision.** Each `CREATE INDEX` in V47 carries a SQL comment naming: (1) the query method on the repository that motivates it (e.g., `-- Motivation: HoldingRepository.findByPortfolioIdAndAssetId; ON DELETE reverse scan when assets.id row is removed`), (2) the assumed selectivity (e.g., `-- Selectivity: 1-2 rows per asset_id at single-user scale; sequential scan would still cost ~200 rows`), (3) the write-cost note (e.g., `-- Write cost: ~16 bytes per row; portfolio_holdings is mutated O(N transactions) so write amplification is sub-millisecond`).
- **Hibernate ddl-auto=validate** must stay green. `CREATE INDEX` does not touch entity columns; the JPA validator does not check indexes; no entity changes needed.
- **No `pg_stat_statements`-coupled assertions.** The new test does NOT depend on `pg_stat_statements` being loaded (it only queries `pg_indexes` + `information_schema`). The overlay is independent and operator-only.
- **`postgresql.conf` is operator-only.** The config file ONLY appears under `monitoring/postgres/`. The default container's `postgresql.conf` is whatever the upstream `postgres:16-alpine` image ships; the overlay mounts our copy when invoked.
- **Rollback boundary.** `git revert` is sufficient; the V47 indexes can be dropped via a forward migration `V48__rollback_30_02_indexes.sql` (Flyway Community has no undo). `IndexCoverageRegressionTest` test-only revert restores the prior coverage assumption. The monitoring overlay revert is a file delete; nothing in the live compose references it.
