<objective>
Add receipt OCR via tess4j as a background worker (Track A9) so receipt uploads acquire searchable text without blocking the upload request.

Purpose: Phase 10.4 shipped receipt photo upload to filesystem; OCR was deferred. Without it, receipts are write-only blobs — the user can't search "Migros 14 Nisan" across saved receipts. tess4j gives Tesseract bindings without requiring a system Tesseract install in the container, and the workload is naturally asynchronous (best-effort background enrichment, not a request-path concern).

Output: Flyway migration adding `ocr_text` and `ocr_status` columns to the receipts table; tess4j-backed worker that processes pending receipts in the background; tessdata packaged for `tur` + `eng`; receipt API exposing the extracted text; frontend showing it under the receipt thumbnail.
</objective>

**Tech stack available:** Spring Boot 3.2 (`@Async`, `@Scheduled`), JPA, Flyway, Java 21 (virtual threads), existing Receipt entity + service from Phase 10.4.
**Established patterns:** Schedulers live under `backend/src/main/java/com/fintrack/scheduler/`; entities under `common/entity/`; service-layer `@Transactional` writes; per-feature DTOs as records. No comments on unchanged code.
**Constraining decisions:**
- Flyway append-only; new column requires `V{n+1}__add_receipt_ocr.sql`.
- AI/Claude integration is out of scope — tess4j is the local-OCR choice.
- Container image must remain self-contained (tessdata bundled, not downloaded at runtime).
**Discovery (Level 2):** tess4j 5.x ships native Tesseract via JNA; tessdata files are not bundled in the jar — they must be placed on disk and pointed at via `Tesseract.setDatapath`. Languages `tur` and `eng` add ~30 MB. Verify license compatibility (Apache 2.0 for tess4j; Apache 2.0 for tessdata-fast).
</context>
