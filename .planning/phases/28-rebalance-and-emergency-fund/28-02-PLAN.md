<objective>
Turn the existing target-allocation drift view (Phase 18 - `AllocationService.summarize` / `AllocationTargets.tsx`) into an actionable rebalance executor (Track G12). After this plan, the owner who has set per-asset-type allocation targets on a portfolio sees a "Rebalance" tab on the portfolio detail page that lists per-holding `BUY` / `SELL` suggestions sized to bring `actual%` back inside a configurable drift tolerance, ticks the rows they want to apply, and clicks `Commit selected` -> the backend creates one `InvestmentTransaction` per ticked row in a single `@Transactional` shot, each emitting `InvestmentTransactionRecordedEvent` so the 25-01 holding projection + 27-03 `AccountBalanceListener` pick up automatically. Mirrors the 27-04 `BankCsvImportService` preview+commit pattern byte-for-byte: preview is `@Transactional(readOnly = true)`, returns a `RebalancePreview(proposalId, targetSummary, suggestions[], driftAfter[])`, generates a server-side `proposalId` (UUID v4) stored in Redis with `30-minute TTL` keyed `rebalance:proposal:<userId>:<proposalId>` -> serialized canonical hash of the `(portfolioId, accountId, suggestions[])` set; commit (`POST .../commit`) takes `RebalanceCommitRequest(proposalId, accountId, selections[])` where `selections[]` is the user-ticked subset of the preview's row indices, recomputes the same canonical hash from the live current state, refuses when the cached `proposalId` is missing OR when the recomputed hash diverges from the cached hash (stale preview - the prices moved or the user added/removed a holding between preview and commit), refuses also when `proposalId` was already committed (Redis key `rebalance:committed:<proposalId>` written by a successful commit). Suggestions are computed at the asset-type level (matching the existing `targetPercent` granularity on `portfolio_allocation_targets`) and then projected onto individual holdings within each asset-type bucket: for an OVERWEIGHT bucket, sell from the holdings within that bucket pro-rata to their current value share until the bucket is back to target; for an UNDERWEIGHT bucket, buy more of the highest-value existing holding in that bucket OR if the bucket has zero holdings flag a `NO_HOLDING_TO_BUY` warning per row (the rebalance executor is NOT a stock-picker; it CANNOT introduce a new asset that the operator hasn't already added). Cash availability check: when the SUM of suggested BUY amounts exceeds `account.currentBalance` (the account picked at preview time, scoped to the user via `AccountRepository.findByIdAndUserIdAndArchivedFalse`), the executor proportionally scales DOWN every BUY suggestion by the `availableCash / requiredCash` ratio (truncated to the asset's `quantityScale`) and surfaces a `CASH_PARTIAL_SCALEDOWN` warning at the summary level; SELL suggestions are NEVER scaled because they REPLENISH cash. Quantity quirks: equities (Asset.AssetType `STOCK` and `FUND`) are forced to integer quantities via `RoundingMode.DOWN` truncation when the suggested fractional quantity falls below an asset-type-specific tolerance; crypto (`CRYPTO`), gold (`GOLD`), currency (`CURRENCY`) keep the asset's full `quantity_scale` (8). The drift tolerance threshold is read from a NEW `user_settings.rebalance_drift_threshold_percent NUMERIC(5,2) NOT NULL DEFAULT 1.00` column added by Flyway `V46__user_settings_rebalance_drift_threshold.sql` (range `0.10..10.00` enforced by single-column CHECK; matches the V45 `user_settings_emergency_fund_targets` pattern); buckets whose `|driftPercent| <= threshold` are EXCLUDED from the suggestion list (no action needed). **Established patterns to mirror (DO NOT improvise - copy these byte-for-byte where applicable):**
- **Preview + commit shape (canonical 27-04 pattern).** `RebalanceService.preview` is `@Transactional(readOnly = true)`, returns a `RebalancePreview` DTO with a server-side `proposalId` (UUID v4). `RebalanceService.commit` is `@Transactional` (writer scope), takes the `proposalId` plus the user-ticked subset of indices, materialises one `InvestmentTransaction` per ticked row, and publishes `InvestmentTransactionRecordedEvent` per row imported (the 27-03 `AccountBalanceListener` rolls each event into `Account.currentBalance` after commit). The commit's hash check guards against stale previews - re-uploading or re-issuing a commit with the same `proposalId` after Redis expiry returns a clean 404 / 409 rather than silently double-committing.
- **Idempotency via Redis-backed proposalId, NOT via a fingerprint column on `investment_transactions`.** Bank CSV import (27-04) used a SHA-256 fingerprint on the persisted row for cross-session dedupe (operator might re-upload the same CSV next month); rebalance proposals are session-scoped (operator generates a preview, ticks rows, commits within minutes), so a Redis TTL key is sufficient and avoids polluting `investment_transactions` with a fingerprint column that has no other purpose. The Redis key shape `rebalance:proposal:<userId>:<proposalId>` -> `<canonical-hash>` matches the 24-04 `webauthn:challenge:<userId>` shape; `rebalance:committed:<proposalId>` 24h sentinel matches the 24-08 anti-replay precedent.
- **Hash check across preview and commit.** `canonicalHash(portfolioId, accountId, suggestions[])` = SHA-256 hex of the JSON-canonicalised tuple of `(portfolioId, accountId, [for each suggestion: assetId, action, quantity, estimatedPriceTry])`. Preview computes once and stores. Commit recomputes from the LIVE state (re-runs the same preview logic) and compares. Mismatch -> `BusinessRuleException("Proposal stale", "REBALANCE_PROPOSAL_STALE")` 409. This is load-bearing because between preview and commit (a) prices may have moved (the live `Asset.price` is the input), (b) the operator may have added/removed a holding via another tab, (c) the operator may have committed a different rebalance against the same account (changing `account.currentBalance`). Re-running the preview computation server-side at commit time is cheap (single-digit ms over <50 holdings) and guarantees the materialised transactions match what the operator saw.
- **Service ownership guards.** `portfolioRepository.findByIdAndUserIdAndActiveTrue(portfolioId, userId)` MUST gate every preview + commit. `accountRepository.findByIdAndUserIdAndArchivedFalse(accountId, userId)` MUST gate every preview + commit. Absent or archived account -> `BusinessRuleException("Account not found", "ACCOUNT_NOT_OWNED")` (24-08 audit-failure-first pattern). Mirrors `BankCsvImportService` byte-for-byte.
- **Audit emission.** Two new `AuditAction` constants `REBALANCE_PREVIEWED` and `REBALANCE_COMMITTED`. `REBALANCE_PREVIEWED` emits on every successful preview (read-only - operator-actionable telemetry, same precedent as `BANK_CSV_PREVIEWED`). `REBALANCE_COMMITTED` emits ONCE per commit, AFTER all `InvestmentTransaction` rows are saved, with detail string `portfolioId=<id> accountId=<id> proposalId=<id> selected=N committed=N`. Each individual `InvestmentTransaction.record(...)` call inside the commit ALSO emits `INVESTMENT_TRANSACTION_CREATED` (the existing audit constant) per row - this is intentional: the audit log carries both the outer "rebalance" event and the per-row trade events so a forensic reader sees the same trade twice (once via the rebalance bundle, once via the individual transaction). The third constant `REBALANCE_FAILED` is NOT introduced - failures route through `auditService.failure(REBALANCE_PREVIEWED|REBALANCE_COMMITTED, ...)` per the 24-08 / 27-04 precedent.

The controller-level validation uses `jakarta.validation` annotations (`@DecimalMin("0.10") @DecimalMax("10.00") @Digits(integer=2, fraction=2) BigDecimal`); validation failures route through `MethodArgumentNotValidException` to the existing `GlobalExceptionHandler`.

Mirrors 28-01's `EmergencyFundService.resolveTargets` pattern.
- **Bucket-to-holding projection algorithm (LOAD-BEARING - executor MUST implement exactly).** Step 1: Compute per-bucket deltas via `AllocationService.summarize(...)` semantics: `bucketDeltaTry[type] = totalValueTry * (targetPercent[type] - actualPercent[type]) / 100`. Step 2: Filter buckets where `|bucketDeltaPercent| <= driftThreshold`. Step 3: For each surviving bucket: if `bucketDelta < 0` (OVERWEIGHT - need to SELL), distribute the SELL amount across the bucket's holdings PRO-RATA to their current value: `sellAmountForHolding = abs(bucketDelta) * (holdingValue / bucketTotalValue)`; cap at `holdingValue` (cannot sell more than you own). If `bucketDelta > 0` (UNDERWEIGHT - need to BUY), find the bucket's HIGHEST-VALUE existing holding (deterministic tiebreak: lower asset.symbol alphabetical) and put the entire BUY amount on it; if the bucket is EMPTY (no existing holdings), emit a single-row warning `NO_HOLDING_TO_BUY` with quantity=0 / amount=0 / `assetId=null` (the row is informational - the operator must add the asset manually before re-previewing). Step 4: For BUY rows, sum `requiredBuyTry`. Compare to `availableCashTry = account.currentBalance`. If `requiredBuyTry > availableCashTry > 0`, scale every BUY row's amount + quantity by `availableCashTry / requiredBuyTry` and add summary warning `CASH_PARTIAL_SCALEDOWN`. If `availableCashTry <= 0`, scale every BUY row to zero and add summary warning `INSUFFICIENT_CASH` (the rows still surface so the operator sees what was intended). Step 5: For STOCK and FUND rows, truncate quantity to integer via `RoundingMode.DOWN` then recompute `estimatedAmountTry = price * truncatedQuantity`; if truncation drops quantity to zero, the row keeps quantity=0 and gains warning `QUANTITY_BELOW_LOT` so the operator knows the bucket is so close to target the integer-lot constraint zeroed it out. Step 6: Compute `projectedDriftAfterPercent` = sum of absolute drift after applying every non-zero suggestion (sanity figure for the UI - "drift drops from 5.2pp to 0.4pp").
- **Quantity precision.** `quantity` BigDecimal scale = 8 (matches `PortfolioHolding.quantity` precision=20 scale=8). For STOCK / FUND, post-truncation scale=0. Estimated price = `Asset.price` at preview time (the live cached value in `assets.price`). Estimated amount = `quantity.multiply(estimatedPriceTry)` rounded HALF_UP scale=4 (matches `InvestmentTransaction.amountTry` precision=20 scale=4).
- **Materialisation through `InvestmentTransactionService.record(...)` reuse vs direct entity save.** The executor MUST reuse `InvestmentTransactionService.record(...)` (NOT save `InvestmentTransaction` rows directly through the repository). Reasons: (a) the existing service performs the SELL guard (`validateSellPossible` - prevents over-selling under a race), (b) emits `INVESTMENT_TRANSACTION_CREATED` audit, (c) publishes `InvestmentTransactionRecordedEvent` so the 25-01 `HoldingProjectionListener` updates the holding and the 27-03 `AccountBalanceListener` rolls the cash. Calling the service from inside `RebalanceService.commit` keeps the contract single-sourced. Each call passes a fresh `RecordTransactionRequest(assetId, txnType, quantity, priceTry, fee=ZERO, txnDate=LocalDate.now(), notes="rebalance:" + proposalId, accountId)` with a stable notes prefix so the audit trail is forensically searchable. `RebalanceService.commit` is `@Transactional` and `InvestmentTransactionService.record` is also `@Transactional` - the inner `record` call participates in the outer transaction by Spring's default propagation (REQUIRED), so a single failure rolls back the entire batch. The 27-03 `AccountBalanceListener` runs at AFTER_COMMIT of the OUTER transaction (one rollup per row, all after the outer commit succeeds).
- **DTO shape mirror (27-04 / 25-01 / 27-03 / 28-01 precedents).** `RebalancePreview` is a Java record. `RebalanceSuggestion` carries explicit string fields for human-readable parts (symbol, asset type display) so the frontend doesn't have to look them up. `RebalanceCommitRequest.selectedIndices` is `List<@NotNull Integer>` validated via Bean Validation (`@NotEmpty @Size(max = 50)`). The `accountId` is required at COMMIT time too - the executor recomputes hash with the same `accountId` the preview was sealed with (mismatch -> stale).
- **No new Flyway constraints on `investment_transactions`.** This plan does NOT add a `rebalance_proposal_id` column on `investment_transactions` - the `notes` field already carries the `"rebalance:<proposalId>"` prefix, and adding a new column for forensic grouping is out of scope (would require an index, would touch hot-path SELECTs, and the `notes` `LIKE 'rebalance:%'` query is fast enough at single-user scale). The forensic question "what trades did rebalance proposal X create?" is answerable via `audit_log.detail LIKE '%proposalId=<id>%'`.
- **Frontend pattern - card placement, NOT route.** Per 28-01's `EmergencyFundSection` precedent of a sub-card on an existing page rather than a dedicated route, the new `RebalanceCard` mounts inline on `PortfolioDetailPage` AFTER the `AllocationTargets` card (the visual flow is: AllocationChart -> AllocationTargets (drift visualisation) -> RebalanceCard (drift -> action)). NO new route under `/portfolio/:id/rebalance`. The card lazy-renders nothing until the operator clicks `Generate suggestions` (first paint shows only the threshold slider + the `AccountPicker` + the button).
- **Frontend hook layering.** `useRebalancePreview` is a `useMutation` (NOT a `useQuery` - the preview is server-state-mutating from a Redis perspective, and the operator triggers it explicitly; query-style auto-refetching would burn Redis keys). `useRebalanceCommit` is a `useMutation` that on success invalidates the five cache keys listed above and pushes a success toast. `useUpdateRebalanceThreshold` is a `useMutation` debounced 400ms by the slider component (the slider's `onValueCommit` fires once on mouse-up; the debounce protects against rapid keyboard arrow presses).
- **Frontend i18n placement.** New top-level `rebalance` namespace in both `tr.json` and `en.json`. Keys planned: `header`, `description`, `driftThresholdLabel`, `driftThresholdHint`, `accountPickerLabel`, `generateButton`, `generateButtonHint`, `commitButton`, `commitButtonHint`, `noDriftEmpty`, `noTargetsEmpty`, `actions.BUY`, `actions.SELL`, `warnings.NO_HOLDING_TO_BUY`, `warnings.QUANTITY_BELOW_LOT`, `warnings.INSUFFICIENT_HOLDING`, `warnings.CASH_PARTIAL_SCALEDOWN`, `warnings.INSUFFICIENT_CASH`, `errors.PROPOSAL_NOT_FOUND`, `errors.PROPOSAL_STALE`, `errors.PROPOSAL_ALREADY_COMMITTED`, `errors.NO_TARGETS`, `errors.ACCOUNT_NOT_OWNED`, `summary.selectedRows`, `summary.estimatedCost`, `summary.availableCash`, `successToast`. Each warning + error key has a one-sentence operator-facing explanation in plain language (no jargon).

**Constraining decisions:**
- **Asset-type bucket granularity.** The existing `portfolio_allocation_targets` table is keyed `(portfolio_id, asset_type)` - targets exist at the asset-type level (CRYPTO / FUND / CURRENCY / GOLD / STOCK / OTHER), NOT per asset. The rebalance executor preserves this granularity: it computes deltas per asset-type bucket and projects them onto holdings within each bucket. Per-asset target weights (`PortfolioHolding.targetWeight` exists but is unused at the AllocationService layer today) are OUT OF SCOPE - introducing per-asset targets would require a new schema + AllocationService rewrite, and the operator's mental model is per-asset-type. Documented in "Decisions Made".
- **Pro-rata SELL distribution within an OVERWEIGHT bucket.** The simplest correct projection. Alternative would be "sell from highest-cost-basis holding first to harvest losses" (tax-loss-harvesting heuristic) - explicitly out of scope; tax helper (27-01) handles the realised-gain side. The pro-rata rule has a clean property: after applying the suggestions, every holding within an overweight bucket retains its WITHIN-BUCKET share, only the TOTAL bucket value drops. Documented in "Decisions Made".
- **Single-holding BUY concentration in an UNDERWEIGHT bucket.** Concentrate the entire BUY amount on the highest-value existing holding (alphabetical tiebreak) rather than splitting across the bucket's holdings. Reasoning: (a) commission/fee minimisation - one trade beats N small trades; (b) the operator can always uncheck the row and add manual fine-grained trades; (c) splitting across N holdings within a bucket pro-rata would dilute meaning - the operator picks "I want 30% in stocks", not "I want 10% in THYAO and 20% in GARAN". Documented in "Decisions Made".
- **No new asset introduction.** The executor CANNOT recommend buying an asset the operator hasn't already added to the portfolio. An empty UNDERWEIGHT bucket gets a single `NO_HOLDING_TO_BUY` informational row. This is load-bearing for safety - the executor is a corrective tool, not a stock picker; recommending which crypto to buy is out of scope and would require a research-grade asset universe. Documented in "Decisions Made".
- **Cash scaling is proportional, not iterative.** When `requiredBuyTry > availableCashTry`, every BUY row is scaled by the same ratio (`availableCashTry / requiredBuyTry`). Alternative would be iterative ("fill the highest-priority bucket first, then the next") - explicit out of scope; proportional scaling is the operator-intent-preserving choice (the operator wanted to bring all underweight buckets toward target; partial-cash should preserve relative bucket priorities, not arbitrarily zero out the smallest buckets). Documented in "Decisions Made".
- **Quantity quirks pinned to asset-type, NOT to a per-asset configuration.** STOCK and FUND truncate to integer; CRYPTO / GOLD / CURRENCY / OTHER use scale=8. This is a simplification - real markets have lot sizes (stocks trade in 100-share lots in some markets), but BIST trades single-share lots and BES funds redeem in fractional shares. Per-asset `min_lot_size` columns are out of scope. The integer-truncation rule prevents the executor from suggesting "sell 3.42 shares of THYAO" which the operator would have to round manually. Documented in "Decisions Made".
- **Drift threshold is per-user (not per-portfolio).** A single setting applies across all portfolios. Per-portfolio thresholds are a polish item; the operator can override at preview time via an optional request field `driftThresholdOverride` (per-call, not persisted) in case they want a tighter threshold on a specific portfolio for a one-off rebalance. Documented in "Decisions Made".
- **30-minute proposal TTL.** Long enough for the operator to step away from the laptop, eat lunch, come back, and commit. Short enough that prices haven't drifted unbearably (live prices update every 5 minutes at most). The hash check fences against the rare case where prices DID drift within 30 minutes - the commit returns 409 with `PROPOSAL_STALE` and the operator re-previews. Documented in "Decisions Made".
- **24-hour committed marker.** A double-commit attempt (operator clicks twice rapidly, browser network retry, etc.) within 24h returns a clean 409 `PROPOSAL_ALREADY_COMMITTED`. Beyond 24h the marker expires; if the operator is somehow still holding a stale `proposalId` after 24h (the open proposal has long since expired), the commit returns 404 `PROPOSAL_NOT_FOUND` instead - both cases prevent double-commit, the difference is the error message clarity. Documented in "Decisions Made".
- **No new endpoint for "list past rebalance proposals".** History is fully covered by `audit_log` queries against `REBALANCE_PREVIEWED` / `REBALANCE_COMMITTED` (24-08 contract) plus `INVESTMENT_TRANSACTION_CREATED` rows whose `notes LIKE 'rebalance:%'`. A dedicated history view would need a `rebalance_proposals` table; out of scope. Documented in "Deferred Enhancements".
- **Rollback boundary:** `git revert` of this plan's commits + drop the V46 column via a fresh migration (Flyway Community has no `undo`). `rebalance:*` Redis keys auto-expire within 24h. No backfill required. Match the 28-01 precedent of describing rollback in the SUMMARY.
- **OpenAPI spec regen is best-effort.** Per 27-01 / 27-02 / 27-03 / 27-04 / 28-01 precedent, `scripts/regen-openapi.sh` fails on a pre-existing 26-01 OpenTelemetry classpath issue. Task 7 verify attempts the regen; if it fails, document under "Deviations from Plan" with the same disclaimer 28-01 used and rely on the new `RebalanceControllerWebMvcTest` for endpoint coverage.

**Issues being addressed:**
- ROADMAP Phase 28 sub-plan 02 line item: `28-02: G12 - Rebalance executor (drift -> buy/sell suggestions -> one-click transaction commit)`. Closed end-to-end after this plan.
- Implicit operator workflow gap: the AllocationTargets card surfaces drift but the action loop ("now go add 6 transactions to fix it") is manual. After this plan, the action loop is one click.

**Concerns being verified:**
- **Race against concurrent transactions.** Between preview and commit, the operator (or a scheduled job) might add an investment transaction in another tab. The hash check catches this (the recomputed hash would differ from the cached) and returns `PROPOSAL_STALE`. The operator re-previews and the new state is reflected.
- **Pro-rata SELL boundary.** When a bucket has a single holding, pro-rata distribution degenerates to "sell all the bucket's overweight from this one holding" - which is correct. When a bucket has zero holdings AND is overweight (impossible? requires the bucket to have value but no holdings - cannot happen because bucket value sums holding values), this branch is never reached.
- **Integer-truncation cumulative drift.** When STOCK/FUND quantities truncate, the cumulative effect is to LEAVE residual drift in those buckets. The `projectedDriftAfterPercent` figure on the preview reflects this honestly (it computes drift AFTER truncation), so the operator sees that committing won't bring drift to zero exactly. Acceptable - the alternative (suggesting fractional shares) is wrong.
- **Cash scaling preserves SELL execution.** SELL rows are NEVER scaled - they free cash, not consume it. The executor explicitly applies scaling only to rows with `action == BUY`.

**Stack changes from prior phases:** None new in this plan. Phase 27 brought the account package + V41-V44 migrations + emergency-fund groundwork. 28-01 brought V45.
