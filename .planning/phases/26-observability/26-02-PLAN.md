<objective>
Stand up self-hosted GlitchTip for backend exception aggregation, wire the Spring Boot 3.2 backend's Sentry SDK to it (GlitchTip is Sentry wire-protocol compatible), and tag every captured event with the running release (`fintrack@<IDENTITY.yaml version>`) plus the git short-sha when available. After this plan: every uncaught exception in `GlobalExceptionHandler.handleGeneral` and every `Exception` thrown from a `@Scheduled` method or a `priceVirtualExecutor` task lands in the GlitchTip web UI with `traceId`/`spanId` (cross-link to Tempo from 26-01), `release`, `environment`, `requestId` (from `RequestLoggingFilter`'s MDC), and the username (from `SecurityContextHolder`) — never the request body, never the JWT, never any field already on the `AuditPiiRedactor` denylist (24-05).

Purpose: Phase 26 closes the observability gap from `tasks/ROADMAP.md` Track E. Sub-plan E2 (this plan) is the error-aggregation foundation that the SLO dashboards in 26-03 consume — GlitchTip's `/api/0/projects/<slug>/stats/` endpoint is the canonical event-rate counter for the error-rate burn-rate alert. The release tag is the load-bearing detail: when the operator runs `/gtr:release` and bumps `IDENTITY.yaml` from `1.1.0` to `1.2.0`, the next exception batch in GlitchTip is filed under the new release automatically; the Sentry-bridge `traceId` field cross-links to a Tempo trace tree by exact id (no manual ID hunt). The `environment` tag separates `development` runs (full sampling, full reporting) from `production` (curated sampling, prod-profile fail-fast).

Output:
1. **GlitchTip stack as a SEPARATE compose overlay at `monitoring/glitchtip/docker-compose.glitchtip.yml`.** The repository's main `docker-compose.yml` is OFF-LIMITS for this plan (project tooling guard `pre_guard_release_files.py` blocks Write/Edit on it, same way `.env.*` is blocked). The overlay defines two new services — `glitchtip-web` (Django app on port 8000, internal-only on `fintrack-net`) and `glitchtip-worker` (Celery worker, no port). It references the existing `postgres` and `redis` containers from the main compose by name (the `fintrack-net` network is declared `external: true` in the overlay so it joins the existing network rather than redefining it). Image pin: `glitchtip/glitchtip:v4.1` (latest stable at execution time — verify on Docker Hub before commit). Postgres init mount points the overlay at `monitoring/glitchtip/init-db.sql` so a fresh Postgres data volume bootstraps the GlitchTip role + database; existing deployments run the SQL by hand once (documented in OPERATIONS.md). Operator brings the stack up with `docker compose -f docker-compose.yml -f monitoring/glitchtip/docker-compose.glitchtip.yml up -d`. New `glitchtip-uploads` named volume in the overlay for attachments / source maps. Behind the existing reverse-proxy/Authelia path so the operator can reach it on `/glitchtip` if they wire that route in their homelab Traefik config; not exposed on the host port directly.
2. **Backend Sentry/GlitchTip SDK integration.** New Maven dependency `io.sentry:sentry-spring-boot-starter-jakarta:7.18.0` (the jakarta-namespaced 7.x line is Spring Boot 3.x compatible; the non-jakarta `sentry-spring-boot-starter` is Boot 2.x only). Configuration in `application.yml` under a new `sentry:` block: DSN env-bound (default empty so dev runs are reporting-disabled by default), `release` env-bound to a value computed at boot (`fintrack@<version>` where version is read from `IDENTITY.yaml` via a new `ReleaseInfoProvider`), `environment` env-bound to `${SPRING_PROFILES_ACTIVE:development}`, `traces-sample-rate=0.0` (we already have OTel tracing from 26-01 — Sentry's tracing is redundant), `send-default-pii=false`, `attach-stacktrace=true`, `max-request-body-size=none` (do NOT attach bodies — sensitive data risk), `in-app-includes=com.fintrack`. A `SentryConfig` `@Configuration` registers a `BeforeSendCallback` that scrubs every event through the existing `AuditPiiRedactor` from 24-05 before transmission, and adds `traceId`/`spanId` from the current Micrometer `Tracer` as event tags so cross-linking back to Tempo is one click. **The `SENTRY_DSN` and `FINTRACK_RELEASE_VERSION` env vars are read by Spring Boot's standard `${ENV:...}` binding from the operator's existing process environment — they are NOT injected via `docker-compose.yml` (off-limits) or `.env.example` (off-limits). The operator places them in their existing `.env` file (which `docker compose` automatically passes to every service) per the `docs/OPERATIONS.md` runbook.**
3. **Release version provider.** New `ReleaseInfoProperties` (Java record bound from a one-line `fintrack.release.version` property) plus a `ReleaseInfoConfig` `@Bean` that reads the version from `IDENTITY.yaml` at boot via a tiny SnakeYAML parse (SnakeYAML is on the classpath transitively via `spring-boot-starter`) and exposes it as `Supplier<String>` for the Sentry config to reference. The version env override (`FINTRACK_RELEASE_VERSION`) wins so a CI pipeline can stamp the release with the exact build's git short-sha (`fintrack@1.1.0+abc1234`).
4. **Production-profile fail-fast.** `ProductionProfileGuard` (24-07) gains one more violation: under `production`, `SENTRY_DSN` must be non-blank — otherwise the operator silently loses error visibility on the prod box. The single `IllegalStateException` payload aggregates this alongside the existing CORS/Redis/JWT/receipt/WebAuthn checks so the boot-time message stays one-shot.
5. **GlitchTip integration test.** A `SentryConfigTest` slice pins (a) the `BeforeSendCallback` strips PII via the same redactor used by 24-05, (b) `traceId`/`spanId` tags are attached when a Micrometer span is active, (c) the SDK is no-op when DSN is blank (dev default), (d) the `release` tag matches `fintrack@<IDENTITY.yaml version>`. No test calls a real GlitchTip endpoint — the SDK's in-memory transport is used instead.

Documented technology choice (no decision checkpoint needed — see Task 1 rationale block): **GlitchTip over Sentry-self-hosted.** Sentry's official self-hosted stack ships ~25 containers (Kafka, Zookeeper, ClickHouse, Snuba, Symbolicator, Vroom, Relay, multiple Redis databases, multiple Postgres databases) and explicitly recommends >= 16 GB RAM. PROJECT.md "Single-user / homelab scale — no premature distributed-systems gear" rules that out. GlitchTip is wire-compatible with the Sentry SDK protocol, requires only a Postgres database (reuses the existing `postgres` container) plus a Redis DB (reuses the existing `redis` container), and runs as 2 small containers (web + Celery worker). The Sentry SDK we're configuring is identical in either case — only the DSN endpoint differs. If the owner ever outgrows GlitchTip, the migration cost is one DSN env var change, no code change. Documented in Decisions Made.
