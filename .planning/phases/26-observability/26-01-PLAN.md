<objective>
Wire OpenTelemetry into the Spring Boot 3.2 backend so every HTTP request, every internal service-to-service call, every external HTTP fetch (the five price clients), and every virtual-thread fan-out span (the new `priceVirtualExecutor` work units from 25-03) emits OTLP traces to a self-hosted Grafana Tempo instance running alongside the existing Prometheus + Grafana monitoring stack. The owner can then open Grafana, pick the Tempo datasource, and follow a single trace through `RestController -> Service -> Repository -> external API` plus the per-source virtual-thread spans for the price-sync path. Trace context (`traceId`, `spanId`) lands in MDC so existing Logback request lines correlate one-to-one with traces.

Purpose: Phase 26 closes the observability gap from `tasks/ROADMAP.md` Track E. Sub-plan E1 (this plan) is the trace pipeline foundation that the next two sub-plans (E2 self-hosted Sentry/GlitchTip exception aggregation, E3 SLI/SLO burn-rate dashboards) consume — Tempo's `traceId` cross-references show up in error reports and on Grafana panels. After this plan: a 30-second live tick is one trace tree with five spans (`refreshLive` orchestrator + four `fetchCrypto / fetchCurrencies / fetchMetals / fetchStocks` virtual-thread children) plus client-level child spans for each WebClient call; an HTTP request like `POST /api/v1/portfolios` is one trace tree starting at the controller, containing the JPA query spans Hibernate emits and the `auditService.success(...)` span the 24-08 audit boundary fires.

Output: Three new Maven dependencies on `backend/pom.xml`: `org.springframework.boot:spring-boot-starter-actuator` is already present; add `io.micrometer:micrometer-tracing-bridge-otel`, `io.opentelemetry:opentelemetry-exporter-otlp`, and `io.opentelemetry.instrumentation:opentelemetry-spring-boot-starter` (Spring Boot 3.2-compatible 2.x line). A new `TracingConfig` `@Configuration` in `backend/src/main/java/com/fintrack/common/config/` that declares the `@Bean`-able `Observation` plumbing for the `priceVirtualExecutor` so virtual-thread span propagation works end-to-end (Spring Boot's auto-config covers Tomcat + WebClient + JPA + Scheduled, but `CompletableFuture.supplyAsync(..., priceVirtualExecutor)` does not propagate the parent `Observation` — it needs a `ContextSnapshot` wrapper). New `tracing` block in `application.yml` with `management.tracing.sampling.probability` env-bound (default 1.0 in dev, 0.1 in prod), `management.otlp.tracing.endpoint` env-bound (default `http://tempo:4318/v1/traces`, the Tempo OTLP/HTTP endpoint), and `management.tracing.propagation.type=w3c` so external systems can stitch traces if the homelab adds a service mesh later. New service `tempo` in `docker-compose.yml` running `grafana/tempo:2.6.0` with a minimal `monitoring/tempo.yml` config (single-binary mode, local storage, OTLP HTTP receiver on 4318 + OTLP gRPC on 4317). Grafana datasource provisioning at `monitoring/grafana/provisioning/datasources/tempo.yml` so the UI shows Tempo alongside Prometheus. `RequestLoggingFilter` updated to read `traceId` / `spanId` from Micrometer's `Tracer` and put them in MDC alongside the existing `requestId` (one-line append, no behaviour change). One new explicit `@Observed` boundary on `PriceSyncService.refreshLive()` and `PriceSyncService.refreshFunds()` so the orchestrator-level span shows up named (the method-level span is otherwise inferred from the bytecode method name, which is fine — but the explicit annotation lets us pin the span name as `price.refresh.live` and `price.refresh.funds` for the dashboards). Tests pinned: a `TracingConfigTest` proves the `Tracer` bean is wired and that `priceVirtualExecutor` Runnable submissions inherit the parent span; a `TracingIntegrationTest` (uses `@AutoConfigureObservability` + the in-memory test exporter) verifies one HTTP request through `PriceController.refresh()` produces a trace tree with the expected span shape (controller → service → 4 fetch children).
</objective>

**Constraining decisions:**
- **Micrometer Tracing bridge over OpenTelemetry Java agent.** Spring Boot 3.x ships first-class observation infra via `io.micrometer.observation`; the bridge `micrometer-tracing-bridge-otel` makes Micrometer the source of truth for Spans + Metrics and OTel the wire format / exporter. Picking the standalone Java agent would mean (a) running a separate `-javaagent:opentelemetry-javaagent.jar` in the Dockerfile, (b) duplicating bytecode-injected spans on top of Micrometer's auto-instrumentation, and (c) losing the `@Observed` annotation we already get for free. The bridge is one POM block + one config block, and Spring Boot 3.2's auto-configuration of `RestTemplateBuilder`, `WebClient.Builder`, `JdbcTemplate`, `KafkaTemplate`, etc. picks up the `Tracer` bean automatically — no per-class wiring. Documented in Decisions Made.
- **OTLP HTTP (4318) over OTLP gRPC (4317).** Tempo accepts both; HTTP/protobuf is one fewer dependency on the backend (no `io.grpc:grpc-netty-shaded`), uses port 4318 by default in Spring Boot's `management.otlp.tracing.endpoint`, and is plenty fast for this single-instance homelab. The Tempo container exposes both receivers (default `tempo.yaml` config), so a future flip to gRPC is one application.yml line away. Documented in Decisions Made.
- **Tempo single-binary mode with local storage.** `grafana/tempo:2.6.0` runs as a single binary by default with a tiny YAML pointing storage at a local volume. No object-store backend (S3/B2/MinIO) is required for the homelab scale. A volume `tempo-data` keeps traces across restarts; retention is left at the default 14 days (configurable later). Documented in Decisions Made.
- **Sampling probability = 1.0 in dev, 0.1 in prod by default.** Single-user homelab traffic is low; dev wants every trace for debugging. Production at 10 % is enough headroom for the burn-rate dashboards in 26-03 without bloating Tempo's storage footprint. Both bound via `MANAGEMENT_TRACING_SAMPLING_PROBABILITY` env so the operator can tune. Documented in Decisions Made.
- **Virtual-thread context propagation.** Spring Boot 3.2 + Micrometer 1.12 auto-propagate the `Observation` context across `@Async`, `@Scheduled`, and `WebClient` calls — but `CompletableFuture.supplyAsync(supplier, executor)` with an *explicit* executor argument bypasses the auto-instrumented default executor. The fix: wrap each fetch supplier in `ContextSnapshotFactory.builder().build().captureAll().wrap(supplier)` (Micrometer's `io.micrometer.context.ContextSnapshot`). To keep the call site clean, add a small `TracingExecutorService` decorator in `TracingConfig` that wraps `priceVirtualExecutor` so any `Runnable` / `Callable` submitted picks up the current `ContextSnapshot`. The wrapped executor replaces the existing bean *only at the inject site for `PriceSyncService`* — we update `PriceSyncService`'s constructor `@Qualifier("priceVirtualExecutor")` to receive the wrapped form via a primary qualifier (`priceVirtualExecutor` is overridden by `TracingConfig`'s decorator bean of the same qualifier; alternatively, name the wrapped one `tracingPriceVirtualExecutor` and update `PriceSyncService` to use the new qualifier — pick the latter so the change is *additive* and the existing `PriceConfigVirtualExecutorTest` keeps testing the raw bean). Documented in Decisions Made.
- **`@Observed` annotation use is minimal and additive.** Spring Boot's auto-instrumentation already creates spans for every `@RestController` method (servlet level) and every `WebClient` call. We add `@Observed(name = "price.refresh.live", contextualName = "price.refresh.live")` on exactly two methods (`refreshLive`, `refreshFunds`) so the orchestrator span is named in a way the dashboards can group on. Avoid sprinkling `@Observed` everywhere — it adds proxy overhead and noise. Documented in Decisions Made.
- **MDC injection of `traceId` / `spanId` is read-only in `RequestLoggingFilter`.** We do *not* introduce a custom `TraceFilter`. `RequestLoggingFilter` already manages MDC for the request lifecycle (`MDC.put / MDC.clear`); we add two more keys (`traceId`, `spanId`) sourced from `tracer.currentSpan().context()` and put them under MDC. If `tracer` is null (e.g. tests with tracing disabled), the filter no-ops the trace keys. Logback pattern is *not* changed in this plan — operator can update it independently if they want trace IDs in the log line; the values are present in MDC either way and Loki already ships the structured fields.
- **Spring Boot starter version pin.** `io.opentelemetry.instrumentation:opentelemetry-spring-boot-starter` ships in two lines: 1.x (Spring Boot 2.x, jakarta-NO) and 2.x (Spring Boot 3.x, jakarta-YES). We pin `2.10.0` (or whatever the latest 2.x release is at the moment of execution; the executor must verify Maven Central before committing the version). The starter pulls `opentelemetry-api`, `opentelemetry-sdk`, and `opentelemetry-exporter-otlp` transitively — but the explicit `opentelemetry-exporter-otlp` declaration in our POM stays as belt-and-braces, so a future starter bump that drops the exporter does not silently break exports.
- **No frontend tracing in this plan.** Browser-side OTel (`@opentelemetry/sdk-trace-web` + `@opentelemetry/instrumentation-fetch`) is a separate concern — the value is span correlation between browser network calls and backend handlers, which is nice-to-have but not load-bearing for the SLO dashboards in 26-03. Documented in Deferred Enhancements.
- **No K6/Gatling load gen, no APDEX scoring in this plan.** The trace data is the foundation; the SLO dashboards (latency p95, error rate, price-sync freshness) live in 26-03. We expose the data here.
- **Caffeine cache stats stay on Micrometer Metrics.** 25-02's `recordStats()` already feeds the Prometheus scrape endpoint via Micrometer's `CaffeineCacheMetrics` (Spring Boot autoconfigures this when both Caffeine + Micrometer are present, which they are). No tracing-side wiring is needed for cache stats; the spans Caffeine emits during `Cache.get / Cache.put` are auto-traced by Micrometer when the surrounding method is observed. Out of scope here.
- **Schedulers carry traces too.** `spring.threads.virtual.enabled=true` (25-03) routed every `@Scheduled` method onto a `SimpleAsyncTaskScheduler` backed by virtual threads. Micrometer's `ScheduledMethodObservationConfiguration` auto-creates an observation context per scheduled run when `management.tracing.sampling.probability > 0` — so `PriceScheduler.scheduledRefresh / scheduledFundRefresh`, `BillReminderScheduler`, `RecurringTemplateScheduler`, `MonthlyReportScheduler`, `SnapshotScheduler`, `AuditRetentionWorker`, `ReceiptOcrWorker.sweep` all get a root span automatically. Documented in Decisions Made.
