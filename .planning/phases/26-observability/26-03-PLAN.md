<objective>
Land the operator-facing SLI/SLO surface for FinTrack on top of the trace + error-aggregation foundations from 26-01 and 26-02. Three SLIs are graphed and alerted on: (a) HTTP request latency p95 per route group (read versus mutating versus auth), (b) HTTP error rate (5xx + selected 4xx) over total request volume, (c) price-sync freshness — the wall-clock age of the OLDEST successful price refresh across the four live providers (CoinGecko, ExchangeRate, Yahoo Finance, PreciousMetals). Realistic homelab SLOs are picked: latency p95 < 500 ms, error rate < 1 %, no provider stale > 6 h. Multi-window multi-burn-rate alerts (Google SRE workbook, two-burn-rate variant) fire from Prometheus alerting rules into Grafana's unified alerting; alert state is visible on the dashboard. The Prometheus + Alertmanager stack ships as a compose overlay following the 26-02 precedent — main `docker-compose.yml` is locked by the `pre_guard_release_files.py` PreToolUse hook. Backend exposes the price-sync-freshness signal via four Micrometer gauges (`fintrack_price_sync_last_success_timestamp_seconds{source=...}`) registered against per-provider `Instant` references that `PriceSyncService` updates after each successful refresh. The dashboard JSON ships in `monitoring/grafana/provisioning/dashboards/fintrack-slo.json` and is auto-loaded by the existing dashboards provisioner (already configured at `monitoring/grafana/provisioning/dashboards/dashboards.yml`).

Purpose: Phase 26 closes the observability gap from `tasks/ROADMAP.md` Track E. Sub-plan E1 (26-01) wired OTel OTLP traces to Tempo. Sub-plan E2 (26-02) wired self-hosted GlitchTip exception aggregation with release tagging and trace-id cross-links. Sub-plan E3 (this plan) is the SLO surface that consumes both: latency / error-rate from `http_server_requests_seconds` (Spring Boot Actuator's auto-instrumented metric, already exported on `/api/actuator/prometheus`), price-sync freshness from new gauges this plan registers, error volume from GlitchTip's stats endpoint as a secondary panel only (not as an alert source — too coarse). After this plan: operator opens Grafana → "FinTrack SLO" dashboard, sees three SLI panels, three SLO budget panels, an active-alerts panel, and a per-provider freshness panel; Alertmanager / Grafana unified alerting fires on multi-burn-rate violations with two windows per SLI.

- **Prometheus alerting via Prometheus rules + Alertmanager, NOT Grafana unified alerting.** Two reasonable choices exist: (a) Prometheus rule files + Alertmanager — the canonical SRE workbook flow; alerts are versioned in Git as `alerts.yml`, the rule evaluator runs in the metrics database itself, Alertmanager handles deduplication / silencing / routing. (b) Grafana unified alerting — alerts live in Grafana's database, configured through the UI or a JSON provisioning file, single pane of glass for graphs + alerts. We pick (a) because: (i) versioned-in-Git rule files are the canonical pattern the SRE workbook describes, (ii) Grafana unified alerting requires a Grafana-side persistence database (sqlite is fine but adds a config surface), (iii) Alertmanager's silencing UI + grouping logic is more operator-friendly than Grafana's at the homelab scale we ship at, (iv) we can ALSO surface the alert state on the Grafana dashboard via the `prometheus_alerts` query — best of both worlds. Documented in Decisions Made.
- **Single Alertmanager instance, default Alertmanager config (no SMTP / Slack / Discord routing in this plan).** The point of this plan is to land the SLO surface and the rule definitions; downstream notification routing is an operator-tuning step. Alertmanager's `alerts` API endpoint is what Grafana queries to populate the active-alerts panel. SMTP / Slack / Discord routing is documented as a follow-up in OPERATIONS.md ("To wire email notifications, edit `monitoring/prometheus/alertmanager.yml` and set the `receiver:` block to your `email_configs:` of choice using the existing `SMTP_*` env vars from the FinTrack mail block").
- **SLI choice: latency p95 over Apdex / latency p99.** p95 is the SRE-default for a single-user homelab — p99 noise is dominated by GC pauses and JIT warmups at this scale and would generate false-positive alerts. Apdex requires picking a satisfaction threshold per route which is hand-tuning we do not need at one-user scale. p95 with a 500 ms SLO is conservative for the actual workload (the only routes with structural latency are `/api/v1/prices/refresh` — which is exempted via a route-group filter — and `/api/v1/admin/audit/...` paginated reads, both of which sit well under 500 ms in practice). Documented in Decisions Made.
- **Route grouping for latency SLO.** Spring Boot's `http_server_requests_seconds` carries a `uri` label that is auto-templatized for `/api/v1/{thing}/{id}` to `/api/v1/{thing}/{id}` (Spring's `WebMvcMetricsAutoConfiguration` does the URI-template substitution). We graph latency p95 per route GROUP via `histogram_quantile(0.95, sum by (le, group) (rate(...)))` where `group` is a Prometheus relabel computed from `uri`: `read` (any GET), `mutating` (POST/PUT/PATCH/DELETE except `/api/v1/auth/*`), `auth` (anything under `/api/v1/auth/**`), `prices` (anything under `/api/v1/prices/**` — exempted from latency alerts because `refreshAll` is structurally slow). The relabel happens in `monitoring/prometheus.yml` via `metric_relabel_configs`. Alternative: do the grouping at query time inside Grafana via `label_replace`. We pick the relabel-at-scrape path because (i) it pushes the cost off Grafana's render path, (ii) the `group` label is then queryable as a first-class dimension in the rule file, and (iii) the alert rule text reads cleaner. Documented in Decisions Made.
- **Error-rate SLI: 5xx only, NOT 4xx.** Spring's `http_server_requests_seconds_count` carries a `status` label. 4xx errors are mostly client mistakes (validation failures, expired tokens) that the operator cannot fix; bundling them into the SLO would create constant low-grade alarm noise from real users mistyping passwords. 5xx alone tracks server health. The rule expression is `sum(rate(http_server_requests_seconds_count{status=~"5..", application="fintrack"}[5m])) / sum(rate(http_server_requests_seconds_count{application="fintrack"}[5m]))`. A small carve-out: `/api/v1/prices/refresh/**` 5xx are emitted by upstream provider failures (CoinGecko down, Yahoo throttling) and are SLO-incidental; we exclude them from the error-rate via a `status` regex that also AND's-NOT on `uri=~"/api/v1/prices/.*"`. Documented in Decisions Made.
- **Freshness SLI: per-source `last_success_timestamp_seconds` gauge.** Prometheus rule expression: `time() - fintrack_price_sync_last_success_timestamp_seconds{source="crypto"} > 6 * 3600` for each source. Four rules total (crypto / currency / metal / stock); fund is intentionally NOT alerted (TEFAS daily-tick model, see objective). This is a `last_seen` style alert and does NOT use multi-window multi-burn-rate math — burn-rate math is for ratio-based SLIs (error rate, latency below threshold) where you can express "we're burning X% of our error budget per hour"; for a freshness SLI, the SLO is binary ("data is fresh / not fresh") and a single threshold-with-duration is the SRE-canonical pattern. Documented in Decisions Made.
- **Burn-rate math for latency p95 + error rate.** Two-burn-rate envelope from the Google SRE workbook chapter "Implementing SLOs":
  - **Fast (page)**: 1 h window × 14.4 burn rate. Formula: `error_budget_burn_rate > 14.4 AND error_budget_burn_rate_short_window > 14.4` over 5 min and 1 h windows respectively. Triggers on a 2 % budget burn over 1 h — operator wakes up.
  - **Slow (ticket)**: 6 h window × 6 burn rate. Formula: `error_budget_burn_rate > 6 AND error_budget_burn_rate_short_window > 6` over 30 min and 6 h windows. Triggers on a 10 % budget burn over 6 h — operator looks at it next morning.
  - The two-burn-rate envelope is the homelab-friendly variant of the four-burn-rate one (which adds a third tier and a smoke-detector tier). At one-user scale, two tiers cover the whole interesting range. Documented in Decisions Made.
- **Recording rules for SLO denominators.** The burn-rate expressions are noisy if computed at alert-evaluation time over raw `_count` series — they involve a rate-over-windows divided by a target. Prometheus recording rules pre-compute the per-window burn rate so both the alert and the dashboard panel read the same series. Three recording rules per SLI, two SLIs that use burn rate (latency, error rate) = 6 recording rules. Names follow the `slo:<sli>:burn_rate<window>` convention. Documented in Decisions Made.
- **Backend metric exposure pattern.** `PriceSyncMetrics` is a `@Component` registering four gauges via `Gauge.builder("fintrack.price.sync.last.success.timestamp.seconds", ref, this::extractEpochSeconds).tag("source", source).register(registry)` (the dot-naming convention follows `BusinessMetrics`; Micrometer translates dots to underscores for Prometheus, so the metric name on the wire is `fintrack_price_sync_last_success_timestamp_seconds`). Gauge value is `Double.NaN` when no successful refresh has been recorded yet (Prometheus shows NaN as a gap; the dashboard panel's "no data" state surfaces correctly). After each successful refresh, `PriceSyncService` calls `metrics.recordSuccess(source, Instant.now())` — the metrics object stores `instant.getEpochSecond()` as a double. NaN-on-empty avoids the "10 minutes of false-positive freshness alerts every cold boot" failure mode. Documented in Decisions Made.
- **`PriceSyncService` constructor parameter is `@Nullable PriceSyncMetrics`.** The existing test fixtures (`PriceSyncServiceTest`, `PriceSyncServiceFundRefreshTest`) construct the service manually via a long `new PriceSyncService(...)` argument list — making the new parameter `@Nullable` and tolerating null in `recordIfPresent(source, ...)` keeps every existing test green without a fixture rewrite. New `PriceSyncServiceMetricsIntegrationTest` exercises the metrics-bean-present path. Documented in Decisions Made.
- **Dashboard JSON ships under provisioning, NOT under runtime-mounted dashboards directory.** The existing main-compose Grafana service mounts BOTH `monitoring/grafana/provisioning` AND `monitoring/grafana/dashboards`. The provisioning loader at `monitoring/grafana/provisioning/dashboards/dashboards.yml` already points at `/var/lib/grafana/dashboards` (the second mount). To stay consistent with the existing two dashboards (`fintrack-overview.json`, `fintrack-business.json`) we drop the new JSON into `monitoring/grafana/dashboards/fintrack-slo.json`. The loader picks it up automatically on the next provisioning interval (30 s). Documented in Decisions Made.
- **Dashboard datasource UIDs.** The existing dashboards reference `prometheus` (the uid set in `monitoring/grafana/provisioning/datasources/prometheus.yml`). We use the same uid so the panel queries resolve under the existing datasource provisioning. The Tempo datasource (uid `tempo`) is referenced by the "Active alerts" panel's drill-down link only — clicking an active alert can deep-link to a Tempo query for traces matching the alert's labels.
- **`monitoring/prometheus.yml` MAY be edited.** The PreToolUse hook scope is `docker-compose.yml`, `CHANGELOG.md`, and `.env.*`; the Prometheus config file is NOT covered. We extend it with a `rule_files: ['/etc/prometheus/alerts.yml']` block and a `metric_relabel_configs:` entry on the backend scrape job to compute the `group` label. The main-compose volume mount line `./monitoring/prometheus.yml:/etc/prometheus/prometheus.yml:ro` continues to resolve unchanged. We add a SECOND mount via the OVERLAY file: `./monitoring/prometheus/alerts.yml:/etc/prometheus/alerts.yml:ro`. NOTE: docker compose does NOT support adding a volume mount to an EXISTING service through an overlay without re-declaring the full `volumes:` list (compose merges arrays by REPLACEMENT, not by union, for service-level keys). Solution: the overlay re-declares the `prometheus` service block with a `volumes:` list that contains the original two mounts PLUS the new `alerts.yml` mount. This is a documented compose pattern; the operator brings up the stack with `docker compose -f docker-compose.yml -f monitoring/prometheus/docker-compose.prometheus.yml up -d` and the overlay's `volumes:` REPLACES the main-compose one (this is the OPPOSITE of the GlitchTip 26-02 case where we merged a single new mount onto `postgres` — that worked because GlitchTip's overlay used the long-form `volumes` syntax that compose CAN merge). See Decisions Made.
