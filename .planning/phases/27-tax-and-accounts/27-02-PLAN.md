**Constraining decisions:**
- **`accounts` is standalone in 27-02.** No FK from `transactions` or `investment_transactions`, no `account_id` column added anywhere outside the new `accounts` table. This is the explicit boundary between 27-02 and 27-03 (per ROADMAP.md "27-03: G2-b — Wire transactions to `account_id`; emergency-fund coverage rolls off the new entity"). Rollback for 27-02 is a single-file `V41__accounts.sql` revert + the new `com.fintrack.account` package + the new frontend tree. If we colocate the FK now, 27-03 is harder to plan and 27-02 has a much wider blast radius.
- **`active` field name became `archived` for clarity.** Portfolio's `active = true` default reads OK for portfolios (an "inactive portfolio" still makes sense) but reads worse for accounts (an "inactive account" sounds like a banking-side closure, not an owner UI choice). Owner-facing copy is "Archive" / "Restore"; persistence column is `is_archived BOOLEAN NOT NULL DEFAULT false`. Repository methods read `archivedFalse`. This is the only deliberate divergence from the Portfolio template — flagged here so the executor doesn't second-guess it.
- **Decimal scale `NUMERIC(20, 8)`.** See "Established patterns" above. Whole-coin denominations are documented; the Hibernate column annotation is `@Column(precision = 20, scale = 8)` so `ddl-auto=validate` matches. The `currentBalance` field carries no `@Builder.Default` — Java's primitive `BigDecimal` defaults to null, but the V41 column is `NOT NULL DEFAULT 0`, so the service constructor always passes the request's opening balance (or `BigDecimal.ZERO` if omitted, falling back to the DB default would defeat the purpose).
- **`MAX_ACCOUNTS_PER_USER = 50`.** Mirrors Portfolio's `MAX_PORTFOLIOS_PER_USER = 20` precedent — an arbitrary high cap that prevents a runaway script (e.g. a test fixture that loops `create()` and forgets to clean up) from filling the table. 50 is generous (the owner won't have 50 accounts; even a maximalist with 4 banks × 3 product lines + 5 brokerages + 3 wallets + 3 cash buckets sits at ~23) and it leaves clear headroom. Documented in "Decisions Made".
- **Duplicate-name guard is case-insensitive AND limited to non-archived rows.** `existsByUserIdAndNameIgnoreCaseAndArchivedFalse(userId, name.trim())` returns true → `BusinessRuleException("Account name already exists", "ACCOUNT_NAME_DUPLICATE")`. An archived account named "Main" does not block a new live "main" — the archived row is preserved as audit history, not as a live constraint. Documented in "Decisions Made".
- **Update path forbids changing `type`.** Mirrors PortfolioService — `UpdateAccountRequest` does NOT carry `type`. If the owner mistypes the type at create time they archive + recreate. Currency IS updatable in this plan because owners do occasionally re-denominate (e.g. an account that was TRY-flagged but actually held EUR all along) — but the SUMMARY documents the trade-off (no historical FX rebase happens; the rebalanced balance is a fresh seed from the operator's perspective).
- **Soft-archive vs hard-delete: soft only.** Matches every other owner-scoped entity in the project (Portfolio, Bill, BudgetRule, RecurringTemplate, User). Hard delete is reserved for a future GDPR-style purge tool that operates across all entity types uniformly — out of scope here. Documented in "Decisions Made".
- **Audit emission mirrors 24-08.** Three new constants in `AuditAction.java`. `auditService.success(AuditAction.ACCOUNT_CREATED, userId, currentUsername(), "id=" + account.getId())` after each write; `auditService.failure(...)` immediately before each `throw new BusinessRuleException(...)`. The `*ServiceAuditTest` Mockito.verify pattern from `PortfolioServiceAuditTest` is copied byte-for-byte (eq + contains matchers, single mock for AuditService, `@InjectMocks AccountService`).
- **No `@Observed` annotations.** The 26-01 servlet observation handler auto-instruments every `@RestController` method; the service layer does sub-millisecond work. Annotation goes on hot batch paths like `PriceSyncService.refreshLive()`, not on owner-driven CRUD where the trace span is one HTTP request long. Documented in "Decisions Made".
- **Multi-currency display is per-account in 27-02.** The frontend page lists each account's `currentBalance` with its `currency` suffix (e.g. "12,500.00 TRY", "1,250.00 USD"). The stat strip shows the per-currency rollup as a comma-separated mini-list (e.g. "TRY 102,500 / USD 3,200 / EUR 800"), NOT a single TRY-equivalent number. True FX-converted rollup needs the price/FX snapshot service to expose a "today's rate" lookup with caching, which is a separate concern — flagged in "Deferred Enhancements". The plan ships the per-currency mini-list because it's the load-bearing display for an owner who actually has multi-currency holdings.
- **No frontend chart, no transaction reconciliation, no balance-history graph.** Balance history needs a daily snapshot job (à la `SnapshotScheduler`) that this plan does not provide. Reconciliation against transactions is 27-03's job. The page is intentionally simple: list, add, edit, archive, view totals. Documented in "Deferred Enhancements".
- **OpenAPI spec regen is best-effort.** Per 27-01-SUMMARY.md, `scripts/regen-openapi.sh` fails on a pre-existing 26-01 OpenTelemetry classpath issue. The executor MUST attempt the regen as Task 5 verify; if it still fails, document under "Deviations from Plan" with the same "verified pre-existing at HEAD" disclaimer 27-01 used and rely on `AccountControllerWebMvcTest` for endpoint coverage.        -- where value sits: bank checking/savings, brokerage cash, crypto wallets,
       -- physical cash. Independent of portfolios and transactions in this plan;
       -- 27-03 wires investment / budget transactions to account_id.

           name                     VARCHAR(100) NOT NULL,
           account_type             VARCHAR(30) NOT NULL,

       @Setter
       @Builder
       @NoArgsConstructor
