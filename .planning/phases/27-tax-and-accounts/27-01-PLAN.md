<objective>
Ship a TR-specific tax helper that the owner opens once a year before filing: it aggregates dividend stoppage (withholding tax) per fiscal year across every active portfolio, surfaces the realized capital-gains figure already produced by `CapitalGainsService` next to the configurable annual exempt threshold, and emits a status (`under` / `approaching` / `over`) with the residual TRY headroom so the user knows whether the next BIST sale will tip them into a declarable position. Tax-year parameters (capital-gains exempt threshold, dividend stoppage rate, BES preferential rate, asset-class scope of the threshold) live in a versioned YAML resource keyed by year — not as Java constants — so each January the owner replaces / appends one block in `tax-parameters-tr.yml` and the report tracks the new figures without a code change.

Purpose: Phase 27 closes Track G of the post-v1 backlog; sub-plan 01 (this plan) is the tax helper end. The next three sub-plans (`27-02` accounts entity, `27-03` transactions wired to accounts, `27-04` TR bank CSV import) consume infra, not data, from this plan, so 27-01 is genuinely independent — `CapitalGainsService` and `DividendRepository` are the two predecessor seams and both already exist (`backend/src/main/java/com/fintrack/report/capitalgains/CapitalGainsService.java`, `backend/src/main/java/com/fintrack/portfolio/dividend/DividendRepository.java`). After this plan: a `GET /api/v1/reports/tax/tr?year=2025` returns `{ year, parameters: { source, capitalGainsThresholdTry, dividendStoppageRate, ... }, dividendStoppage: { totalGrossTry, totalWithholdingTry, totalNetTry, byAsset: [...] }, capitalGains: { realizedTry, thresholdTry, headroomTry, status: 'under'|'approaching'|'over' }, warnings: [...] }`. A new "Tax (TR)" report page links from `/analytics`, sits next to the existing `/reports/capital-gains` route, and renders four cards (status badge, realized YTD, threshold, headroom) plus a per-asset stoppage table. Crossing 80 % of the threshold flips the status from `under` to `approaching`; crossing 100 % flips to `over` and surfaces a warning string the user can copy into their accountant's email.

Output: One new YAML resource `backend/src/main/resources/tax/tax-parameters-tr.yml` with two seeded year entries (`2024`, `2025`) — all numbers come from a one-shot `Maliye Bakanlığı / GİB` web check at execution time and the executor records the exact source URL in the file header. New `com.fintrack.report.tax.tr` package: `TrTaxParameters` immutable record (one tax year), `TrTaxParametersLoader` (`@Component`, parses the YAML on startup via SnakeYAML which is already on the classpath via Sentry's transitive `snakeyaml` from 26-02 — verified through `mvn dependency:tree`; if missing, add `org.yaml:snakeyaml` directly with no version override so Spring Boot's BOM wins), `TrTaxService` aggregating realized capital gain (delegated to `CapitalGainsService`), aggregated dividend stoppage (delegated to a new `DividendRepository.sumStoppageByPortfoliosAndRange` query), and the threshold comparison; `TrTaxController` mapping `GET /api/v1/reports/tax/tr` with the existing JWT-auth pattern; `TrTaxReportResponse` plus three nested records. New repository method on `DividendRepository`: `sumStoppageByPortfoliosAndRange(List<UUID> portfolioIds, LocalDate from, LocalDate to)` (mirror of the existing `sumNetByPortfoliosAndRange`). One new frontend page `frontend/src/pages/TrTaxPage.tsx` lazy-loaded from `App.tsx` at `/reports/tax/tr`, one hook `useTrTaxReport`, one API module `taxtr.api.ts`, one types file `tax.types.ts`. Existing `AnalyticsPage` gets one new card linking to the report (additive). i18n keys land in both `tr.json` and `en.json` under a new `taxTr.*` namespace. Tests: `TrTaxParametersLoaderTest` (4 — happy path, missing year, malformed yml, fallback when no file present), `TrTaxServiceTest` (≈10 — under/approaching/over status across boundary years, dividend aggregation, missing-parameters path, multi-portfolio aggregation, year-defaulting to current calendar year, timezone-aware year derivation honouring the user's `UserSettings.timezone`), `TrTaxControllerWebMvcTest` (≈4 — happy path, no-params-for-year fallback, year filter required positive integer, 401 without auth), and one frontend test `useTrTaxReport.test.tsx` (1 — query key + URL shape). Existing `CapitalGainsServiceTest` is untouched; the new service consumes `CapitalGainsService.compute(...)` as a black box.

**Constraining decisions:**
- **Tax parameters externalized as YAML keyed by year, NOT as Java constants and NOT as a Flyway-seeded DB table.** The owner will edit `backend/src/main/resources/tax/tax-parameters-tr.yml` once a year (a thirty-second job) and rebuild — versus the alternatives:
   1. Java constants → forces a code change + deploy each January, and inflates the diff with hard-coded numbers a non-developer can't audit.
   2. Flyway migration → forces a new `V{n}__tr_tax_parameters_2026.sql` per year and the schema becomes append-only history of tax constants, which is the wrong shape (constants aren't reportable data, they're configuration).
   3. Admin-settings table seeded via existing `AdminSettings` infrastructure → over-engineered for a single-owner homelab; no UI to edit TRY thresholds, no reason to allow runtime mutation.
   YAML keyed by year is the simplest fit: append a block, redeploy, done. The file ships with `2024` + `2025` seeded; `2026` will be added at the next New Year.
   Documented in Decisions Made.
- **Threshold proximity bands are hard-coded at 80 % / 100 %** — `under` (< 80 %), `approaching` (80–100 %), `over` (> 100 %). The bands are a UX convention, not a tax rule, so they live in `TrTaxService` as `private static final BigDecimal APPROACHING_RATIO = new BigDecimal("0.80");`. Documented in Decisions Made.
- **Year defaulting honours `UserSettings.timezone`.** When `?year=` is omitted, the controller derives the current year via `LocalDate.now(zoneId)` where `zoneId` comes from `UserSettings.timezone` (Phase 8 V8 migration). Default to `Europe/Istanbul` if the user has no setting. Avoids the bug where an owner traveling overseas sees the wrong fiscal year. Documented in Decisions Made.
- **Stoppage scope is dividend stoppage only.** The TR tax code distinguishes dividend withholding (`stopaj`), capital-gains withholding (broker pre-collection on equities held < 1 year), and FX stoppage. Phase 27-01 covers ONLY dividend stoppage because that's the data we already capture (`Dividend.withholding_tax` is on every record since V34). Equity capital-gains and FX stoppage are deferred to a future plan because the platform doesn't capture broker-side withholding today. Documented in Deferred Enhancements.
- **Capital-gains threshold scope follows the YAML file.** Each year block declares which asset classes the threshold applies to via `appliesTo: [STOCK]` (matching `Asset.AssetType` enum names verbatim). 2025 TR rules apply the threshold to listed equities sold within one year of acquisition; the `applies-to` list lets the YAML file express that, and `TrTaxService` filters realized events from `CapitalGainsService.events` accordingly when computing the headline figure. Crypto, gold, funds — all currently realize-and-exempt under TR rules, so they appear in the response but don't count against the threshold. Documented in Decisions Made.
- **No new migration.** This plan adds zero schema. `Dividend.withholding_tax` (V34) is the read source. `tax-parameters-tr.yml` is YAML-on-classpath. `TrTaxService` is read-only and computes on the fly. The plan touches Java, YAML, frontend, tests — no Flyway file.
- **Service-level reuse of `CapitalGainsService`.** `TrTaxService` constructor takes a `CapitalGainsService` dependency and calls `capitalGainsService.compute(userId, year)` to get realized gain + dividend net. The threshold comparison + parameter lookup + status banding are the *only* new logic. Avoids duplicating the FIFO lot-tracking that `CapitalGainsService` already encodes. Documented in Decisions Made.
- **Single-locale resource file.** The plan ships only `tax-parameters-tr.yml`. A future locale (US, DE, …) would add `tax-parameters-{locale}.yml` and a sibling `UsTaxService` / `DeTaxService`. Generic `TaxParameters` interfaces are deferred — premature abstraction. Documented in Deferred Enhancements.
- **No Excel / CSV export in this plan.** The owner reads the page in the browser, copies the figures, pastes into the GİB e-beyanname form. PDF/CSV export of the tax report is a separate plan (could be folded into Phase 13's report-export track or shipped on its own).
- **No alerting / scheduled job.** A weekly email "you crossed 80 % of the threshold" is a `@Scheduled` worker, not a report endpoint. Out of scope; deferred. Documented in Deferred Enhancements.
- **No multi-currency complications.** The threshold is denominated in TRY (the owner's domicile + `Dividend.netAmountTry` / `CapitalGainsResponse.realizedGain` already pivot to TRY). The YAML stores `capitalGainsThresholdTry: 158000` as a plain number; no currency conversion happens in the service.
- **No frontend chart in this plan.** The page renders four cards + a table. A "headroom over time" Recharts line chart is deferred — it requires per-month rolling realized gain, which `CapitalGainsService` does not currently expose. Out of scope.
- **OTel/Sentry/Tempo (Phases 26) come along for free.** No explicit `@Observed` annotation. The controller endpoint is auto-instrumented (26-01 confirmed servlet observation handler is live for every `@RestController`); errors flow through `GlobalExceptionHandler` and Sentry's `BeforeSendCallback` from 26-02 attaches `trace.id`/`span.id`/`request.id`.
