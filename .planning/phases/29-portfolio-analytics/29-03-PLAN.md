<objective>
Ship Track G6 — Monte Carlo net-worth projection — as the third and FINAL plan of Phase 29 "Portfolio Analytics". The owner already has Phase 19 (12-month cash flow projection in `CashFlowProjectionService` + scenario sliders) and Phase 12's deterministic FIRE calculator (`FireService.compute(...)` returns a single-trajectory net-worth path under fixed expected return + monthly contribution). Both views collapse uncertainty into a single expected line. What is still missing: a stochastic projection that answers "what is the spread of my net-worth in 20 years given the volatility of each asset class?" — the median path is the FIRE line, but the operator wants the p10 / p25 / p75 / p90 envelope around it so they can size their drawdown plan against the downside, not against the expected case. This plan adds a new server-side endpoint `POST /api/v1/analytics/monte-carlo` returning a per-year percentile fan (p10 / p25 / p50 / p75 / p90) of simulated terminal net-worth values, plus headline summary statistics (mean, p10, p50, p90, success-probability against an optional target). Body: `MonteCarloRequest(int horizonYears, int iterations, BigDecimal currentNetWorth, BigDecimal monthlyContribution, BigDecimal targetNetWorth (nullable), List<AllocationClassInput> allocations)` where `AllocationClassInput(AssetClass assetClass, BigDecimal weight, BigDecimal annualMeanReturn, BigDecimal annualStdDev)` carries one row per asset class. Defaults are exposed at `GET /api/v1/analytics/monte-carlo/defaults` returning the canonical per-class mean / stddev tuples + the recommended `iterations=10000`, `horizonYears=20` so the frontend can hit Run on first render without configuration. The ten-thousand-path inner loop is per-iteration sequential (one path = `horizonYears * 12` monthly steps, one normal draw per class per step under that class's weight, contribution applied at each step, terminal value captured) but iterations themselves fan out across a virtual-thread executor reusing the 25-03 / 26-01 `tracingPriceVirtualExecutor` decorator pattern via a new colocated `monteCarloVirtualExecutor` `@Bean` so the ~150-300ms compute does not pin a Tomcat platform thread. Per-year percentile aggregation walks the iteration matrix at each year boundary (12, 24, 36, ..., horizonYears * 12 monthly steps) and computes the five percentiles via `Arrays.sort` + linear interpolation. Cache the response on Caffeine via `@Cacheable("analytics:monteCarlo")` keyed by `(userId, normalised request hash)` with a 60-second TTL — same inputs hit the same percentiles within a session even when the operator clicks Run again. Cache invalidation rides the existing 25-02 / 29-01 / 29-02 pattern: `@CacheEvict(value = "analytics:monteCarlo", allEntries = true)` lands ONLY on `PriceSyncService.persistUpdates(...)` and `refreshAsset(...)` — same write-adjacency profile as 29-02 (price drift changes the operator's current net worth which is the simulation's starting point). The endpoint is `@Observed(name = "analytics.monteCarlo")` on the orchestrator method; controller stays thin per the 26-01 / 29-01 / 29-02 precedent. Per-class default mean / stddev tuples live in a versioned classpath YAML at `backend/src/main/resources/analytics/monte-carlo-defaults.yml` keyed by `AssetClass` enum name (mirrors the 27-01 `tax-parameters-tr.yml` loader pattern byte-for-byte) so the owner can edit historical-norm assumptions without a Java constant change or a Flyway migration. Seeded values (rationale documented in the YAML header):

- STOCK 7.0% / 18.0% (S&P 500 long-run real-return + post-2000 vol)
- BOND 3.0% / 6.0% (US 10y Treasury long-run nominal)
- CASH 1.0% / 1.0% (TR mevduat post-tax baseline)
- CRYPTO 20.0% / 60.0% (BTC 2014-2024 annualised)
- GOLD 5.0% / 15.0% (XAU long-run nominal)
- FUND 6.0% / 14.0% (TEFAS YAT mid-cap aggregate baseline)
- CURRENCY 0.0% / 8.0% (TRY-anchored carry-neutral assumption)
- OTHER 5.0% / 12.0% (catch-all conservative split)

The eight class names mirror `Asset.AssetType` exactly (CRYPTO / STOCK / GOLD / FUND / CURRENCY / OTHER plus the new BOND and CASH classes) — the new `AssetClass` enum lives in the new `com.fintrack.analytics.montecarlo` feature package and is NOT a renaming of `Asset.AssetType`; the simulation operates on conceptual macro-classes (BOND and CASH have no `AssetType` analogue), the asset-master enum stays unchanged. The owner enters weights manually (default fan: STOCK 50% / BOND 20% / CASH 10% / CRYPTO 10% / GOLD 10%) — the simulation does NOT auto-derive weights from the operator's actual holdings in v1 because allocation drift, multi-portfolio aggregation, and FX mapping make the auto-derivation unreliable; documented in "Decisions Made" + "Deferred Enhancements". Frontend ships a fourth tab `Monte Carlo` on `AnalyticsPage` (mirrors the 29-01 / 29-02 tab pattern — `AnalyticsTab` union extends to `'overview' | 'compare' | 'correlations' | 'monteCarlo'`). The `MonteCarloProjection` component owns the per-class allocation editor (rows of `{class, weight%, mean%, stddev%}` pre-filled from the defaults endpoint), an iterations slider (`1000..10000` step 1000, default 10000), a horizon slider (`5..50` years, default 20), a current net-worth input (pre-filled from `useFireProjection()` so the operator does NOT have to retype their current value — falls back to a manual input when the FIRE summary is unavailable), a monthly contribution input (same pre-fill from FIRE), an optional target input (defaults to the FIRE `targetNumber`), and a Run button. The Recharts area chart shows the percentile fan (`<Area>` for p10-p90 outer band + p25-p75 inner band + `<Line>` for p50 median) over the horizon, with summary stat cards underneath (median final value, p10 downside, p90 upside, success probability vs target). All four cards format via `formatTRY` / `formatPercent`. New i18n keys land under `analytics.monteCarlo.*` in BOTH `tr.json` AND `en.json`. The `AnalyticsTabsBar` widens to four entries; the `MonteCarloProjection` component is lazy-mounted only when the tab is active so the defaults fetch + form state do not pay the cost on the Overview tab.

Purpose: The owner asks "if I keep contributing 30k/month for 20 years, how much could I have? And how bad could it get?" Today the FIRE calculator answers the first question with a single number (assumes 7% return, no variance); the cash-flow projection answers it for 12 months. Neither view exposes the volatility envelope. After this plan ships, the workflow is: open `/analytics`, click the `Monte Carlo` tab, hit Run (defaults pre-loaded), see the fan chart of `[p10, p25, p50, p75, p90]` terminal values per year + summary stats. The operator can tweak per-class weights / mean / stddev to test scenarios ("what if BTC stops returning 20%?") and re-run; the chart re-renders in ~300ms thanks to the virtual-thread fan-out + Caffeine cache. **Constraining decisions:**
- **No new Flyway migration.** Defaults live in a YAML resource — no admin-settings table, no schema work. Future enhancements (saved scenarios, per-user override of class defaults) would warrant a migration; explicitly out of scope.
- **No FireService dependency.** The simulation does NOT compose `FireService.compute(...)` to derive `currentNetWorth` — the request body always carries `currentNetWorth` and `monthlyContribution` explicitly, and the frontend pre-fills both from the FIRE response client-side. Keeps `MonteCarloService` standalone (smaller blast radius, simpler tests, no transitive `BudgetService` / `MonthlySummaryRepository` deps). Documented in "Decisions Made".
- **No auto-derivation of allocation weights from holdings.** v1 weights are operator-entered (default 50/20/10/10/10 fan from the YAML). Auto-deriving from `usePortfolios()` × `holdings` would require: walking holdings × asset master to bucket each holding into an `AssetClass`, summing values per bucket, normalising to weights. Three failure modes the auto-derivation introduces: (a) `Asset.AssetType.OTHER` lumps together unrelated bonds + commodities + currency, breaking the simulation's class semantics; (b) FX-denominated holdings need TRY conversion to weight-share correctly, which the FX layer does not yet expose; (c) the operator's mental model is "what if my mix were 60/40 instead of 50/30/10/10?" — driven from a hypothesised allocation, not from the actual one. The default plan keeps weights manual; auto-derivation goes to "Deferred Enhancements". Documented in "Decisions Made".
- **No correlation matrix between classes.** Each class draws independently from its `N(mean, stddev)`. Modelling a STOCK-BOND correlation of -0.2 (the historical norm) would require the operator to enter or accept a class-correlation matrix, plus a Cholesky decomposition step inside the inner loop. This is materially more complex and the v1 fan chart's headline insight (the spread, not the joint dynamics) is preserved without it. Documented in "Decisions Made" + "Deferred Enhancements".
- **No log-normal alternative.** The simulation samples returns from `N(mean, stddev)` not `LogN(mean, stddev)`. Log-normal is the textbook-correct distribution for compounded returns over long horizons (it bounds the lower tail at zero and lets the upper tail diverge). Normal is simpler, pedagogically clearer, and the 20-year horizon's variance is small enough that the visual difference between the two is < 5% on the percentile fan. Documented in "Deferred Enhancements".
- **No saved scenarios.** Saving "BTC-bear case" or "60/40 baseline" as a named view requires a new `monte_carlo_scenarios` table + CRUD endpoints. Out of scope. Documented in "Deferred Enhancements".
- **No CSV export.** The chart is a screen-first analysis; the data is small enough that the operator can paste percentile values into Excel manually if needed. Out of scope.
- **No WebSocket push.** Re-running the simulation is a manual Run-button action; live re-computation on price ticks would invert the cache contract (every tick invalidates) and pin compute on the price-sync hot path. Out of scope.
- **Iteration cap 10000.** Beyond 10000 iterations the percentile noise floor flattens and the marginal compute cost dominates the marginal accuracy gain. The cap is enforced server-side via `@Max(10000)` Bean Validation + service-layer re-check (defensive). The frontend slider maxes out at 10000.
- **Horizon cap 50 years.** A 50-year simulation produces 600 monthly steps × 10000 iterations = 6M operations per class × 8 classes = 48M operations worst case. At ~100ns/operation on a modern JVM with virtual threads that is ~5 seconds, which is the threshold beyond which the operator perceives the request as broken. The cap is enforced via `@Max(50)`.
- **Cache TTL 60 seconds.** Mirrors 29-01 / 29-02. The cache is keyed by the request hash so repeated Run-button clicks within the session hit the cache; the 60s TTL ensures fresh data after a manual price-sync.
- **Rollback boundary:** `git revert` of this plan's commits is sufficient — no Flyway migration, no schema change, no dep addition. Match the 29-01 / 29-02 precedent of describing the trivial rollback in the SUMMARY.
