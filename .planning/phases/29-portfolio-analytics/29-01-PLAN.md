<objective>
Ship Track G4 — multi-portfolio side-by-side comparison — as the first plan of Phase 29 "Portfolio Analytics". The owner already has per-portfolio history (Phase 18: `SnapshotController` at `GET /api/v1/portfolios/{portfolioId}/history`, `PortfolioHistoryChart`) and a global aggregate netWorth chart on `/analytics` (`usePortfolioSnapshotsAggregate` walks every portfolio and folds value+cost into one line). What is still missing: the ability to look at portfolios A vs B vs C *separately on the same chart* over a chosen range, with the percentage-change overlay so a 10k portfolio is visually comparable to a 1M portfolio. This plan adds a new server-side endpoint `GET /api/v1/analytics/portfolios/compare?ids=A,B,C&from=YYYY-MM-DD&to=YYYY-MM-DD` returning, per portfolio, an array of `{date, totalValueTry, totalCostTry, unrealizedPnlTry, realizedPnlTry, totalPnlTry}` points sourced from the existing `PortfolioSnapshot` rows (no new tables, no new migrations). Realized P&L per snapshot date is derived from `InvestmentTransaction` SELL rows owned by the portfolio whose `transactionDate <= snapshot.date` — sum of `(unitPrice - avgCost) * quantity` at sell time. Range presets `1M / 3M / YTD / 1Y / ALL` ride on the existing `DateRangePicker` (`frontend/src/components/ui/date-range-picker.tsx` already exposes `defaultDateRange()` + `filterByRange`). Multi-currency: snapshots are already pre-aggregated in TRY (`PortfolioSnapshot.totalValueTry / totalCostTry`); the response stays TRY-only and a single `currency` field at the top level of the response documents that explicitly. The frontend ships a new tab on the existing `/analytics` page (NOT a new route — the existing page already owns date-range and benchmarks UX, so a Tabs control "Overview / Compare" inside `AnalyticsPage` is the cleaner placement than a sidebar entry) plus a new component `PortfolioComparisonChart` that mirrors the multi-line shape of `BenchmarkOverlayChart` (one Recharts `<Line>` per portfolio, dashed when overlapping the start, normalised-percentage default Y axis, absolute-TRY toggle). The portfolio multi-select reuses shadcn primitives the project already has (`Checkbox` + `Popover` + `Button` — no new shadcn components). The endpoint is `@Transactional(readOnly = true)`, marked `@Observed(name = "analytics.portfolios.compare")` per the 26-01 boundary precedent, and cached on Caffeine via `@Cacheable("analytics:portfolios:compare")` keyed by `(userId, sortedIdsCsv, from, to)` with a 60-second TTL. Cache invalidation rides the existing 25-02 pattern: snapshot writes trigger `@CacheEvict(value = "analytics:portfolios:compare", allEntries = true)` on `SnapshotService.captureDaily` and on the per-row upsert in `SnapshotService.captureNow` if it exists (verify in the executor task — if not, evict only on `captureDaily`).

Purpose: The owner wants to know "is my BES fund pulling its weight against my individual portfolio?" without exporting CSVs. After this plan ships, the workflow is: open `/analytics`, click the "Compare" tab, tick two-or-more portfolios, pick a range preset, see the percentage-change overlay (default) or absolute TRY (toggle), hover for synchronised tooltips showing every selected portfolio's value at that date. **Constraining decisions:**
- **No new Flyway migration.** The plan is read-only over `portfolio_snapshots` and `transactions` (the investment transactions table; verify table name in Task 1 — possibly `portfolio_transactions` per Phase 1's convention). V47 is reserved for any future analytics plan in this phase that legitimately needs a denormalised table; this plan does not.
- **Multi-currency is TRY-only at the API for v1.** `PortfolioSnapshot` already aggregates in TRY; honouring user-preferred display currency requires either an FX conversion service (deferred from 27-03 / 28-01) or persisting alternate-currency snapshots (out of scope). The response field `currency: "TRY"` makes this explicit and forward-compatible. Documented in "Decisions Made" + "Deferred Enhancements".
- **Realised P&L is approximate (running average).** Precise lot-level FIFO realised P&L is owned by the existing `CapitalGainsService` (Phase 18, `/api/v1/reports/capital-gains`). The compare view uses a simpler "value at sell minus current avg cost basis × quantity" approximation so it can be computed without re-running FIFO across every snapshot date. Document explicitly in DTO JavaDoc + `docs/API.md` + the Compare tab's footnote (i18n key `analytics.compare.realisedPnlNote`). If the executor finds that the project's `InvestmentTransaction` entity DOES persist the at-sale cost basis precisely (e.g. a `costBasisAtSaleTry` column added by some prior plan), upgrade the approximation to the precise value silently — same DTO shape. Documented in "Decisions Made".
- **Maximum 10 portfolios per request.** Beyond 10 the chart legend gets unreadable and the SQL fan-out (10 × 2 round-trips per portfolio for the snapshot + transaction queries) starts to hurt the cache-miss latency. Bound enforced in the service layer with `BusinessRuleException("Too many portfolios in compare request", "COMPARE_TOO_MANY")`. Frontend disables additional checkboxes when 10 are selected and surfaces a tooltip explaining the cap.
- **Cache TTL 60 seconds.** Snapshots update once per day; benchmarks cache at 15 minutes (see `useBenchmarks` hook). The compare endpoint is more interactive (toggling portfolios, switching ranges) so a 60-second TTL balances "instant repeat clicks within a session" against "fresh data after a manual snapshot capture or a SELL transaction".
