The owner has already shipped 29-01 (multi-portfolio comparison overlay) and Phase 18 (per-portfolio history chart with benchmark overlay against BIST 100 / S&P 500 / gold) — both consume aggregated TRY value series. This plan adds a new server-side endpoint `GET /api/v1/analytics/correlations?assetIds=A,B,C&from=YYYY-MM-DD&to=YYYY-MM-DD&method=PEARSON` returning a square correlation matrix as `{ assetIds: [...], assetSymbols: [...], assetNames: [...], matrix: number[][], dataPoints: number[][], samplePeriod: { from, to }, method: "PEARSON" }` sourced from the existing `price_history` table (no new migration; the table already keeps 90 days of daily price points per asset). Daily returns are computed as `log(p_t / p_{t-1})` for chronologically adjacent close-of-day rows per asset (log returns are the standard for correlation work; document the choice). Sparse-data alignment: the server **drops dates where any of the requested assets has no price** (intersection-only) — forward-fill biases correlation toward 1.0 because flat days masquerade as zero-return days, so intersection is the honest move. The `method` query param accepts `PEARSON` (default, the standard ask) or `SPEARMAN` (rank-based, robust to outliers — included as a secondary option since the only branch on top of Pearson is rank-encoding the returns first). Cap at 25 assets per request: 25² = 625 cells in the response, frontend renders 25×25 cells in a CSS grid (~625 `<div>`s — well within React's render budget; ~700 KB DOM footprint at most). Compute log returns from those overlapping dates' prices ordered chronologically. The pair-by-pair intersection (not a global intersection across all N assets) is the correct semantics — using a global N-way intersection biases the matrix toward fewer overlapping days when one asset has gaps, even when the other pair would have plenty. Document this trade-off (pair-wise intersection is the standard finance convention) in JavaDoc + `docs/API.md`. Implementation: load each asset's series once into a `Map<LocalDate, BigDecimal>` keyed by `recordedAt.atZone(UTC).toLocalDate()` (collapse multiple intra-day rows by keeping the latest of each day — the price-sync pipeline does write multiple rows per day; verify in Task 1; the right collapse is "keep the latest `recordedAt` for each calendar date"); iterate the matrix `i ∈ [0, N), j ∈ [i+1, N)` and for each pair compute the intersection of date keys, sort, derive the log-return arrays, run the Pearson kernel. The `dataPoints[i][j]` cell is the count of overlapping dates AFTER differencing (so a 30-day intersection produces 29 returns; record 29 in the cell). Diagonal `dataPoints[i][i]` is the per-asset row count for self.
- **Pearson kernel:** `corr(x, y) = sum((x_t - mean_x)(y_t - mean_y)) / sqrt(sum((x_t - mean_x)^2) * sum((y_t - mean_y)^2))`. Use `double` (not `BigDecimal`) — financial precision is not required for a correlation coefficient and `double` keeps the kernel readable; the only place precision matters is the input price ratios where we already use the existing `BigDecimal` `price` column; convert to `double` once via `priceCurrent.doubleValue() / pricePrev.doubleValue()` then `Math.log(...)`. Edge cases: `n < 2` overlapping returns → `null`; either stddev = 0 → `null`; otherwise return the finite value clipped to `[-1.0, 1.0]` (numerical wobble can produce 1.0000000002).
- **Spearman kernel:** Replace each return series with its rank (1-based, ties resolved via average rank), then run the same Pearson kernel on the ranks. Document the tie-handling explicitly. The implementation lives next to the Pearson kernel as `private static double[] toRanks(double[] xs)`.

**Constraining decisions:**
- **No new Flyway migration.** The plan is read-only over `price_history` (existing in V1). V47 is reserved for a future plan that legitimately needs schema work; this plan does not.
- **Method enum is server-side normative.** The enum `CorrelationMethod { PEARSON, SPEARMAN }` is the canonical contract; the response always echoes the method back as the upper-cased enum name (so the frontend's `method?: 'PEARSON' | 'SPEARMAN'` literal type aligns). No third method (Kendall's tau, distance correlation, etc.) is in scope — the matrix workflow is "Pearson by default, Spearman if the operator suspects outliers". Documented in "Deferred Enhancements".
- **Sparse-data alignment is pair-wise intersection, NOT forward-fill.** Forward-fill biases correlation toward 1.0 (flat days look like zero-return-day correlations). Intersection is the honest move. Document explicitly in DTO JavaDoc + `docs/API.md` + the Correlations tab's footnote (i18n key `analytics.correlations.intersectionNote`).
- **90-day window cap.** `price_history` retention is 90 days (per the V1 schema comment "kept 90 days"). The frontend's range picker maxes out at `90D`; the server defaults to "last 90 days" when no range is given and clamps `from` to `today - 90d` if the operator passes an older date (returning the clamped period in `samplePeriod`). Documented in "Decisions Made" + footnote.
- **25-asset cap per request.** Beyond 25 the heatmap becomes visually unreadable (cells < 24px on a 1280px page), the response payload grows to N² cells, and the SQL fan-out (25 × 1 round-trip per asset for the price-history query) starts to hurt cache-miss latency. Bound enforced server-side with `BusinessRuleException("Too many assets in correlation request", "CORRELATION_TOO_MANY")`. Frontend disables additional checkboxes when 25 are selected.
- **Cache TTL 60 seconds.** Prices update via the `PriceSyncService` scheduler (verify cadence in Task 1; benchmarks are 15-minute, internal asset prices may be sub-hour). The compare endpoint shipped at 60s in 29-01 and the correlation surface has the same write-adjacency profile. Mirror exactly.
- **No WebSocket push for the matrix.** The `/api/v1/ws` STOMP channel broadcasts price ticks — keeping the matrix live would require server-side incremental recomputation of pairwise correlations on each tick, which is materially more complex than the periodic-recompute model. Out of scope.
- **No CSV export of the matrix.** The operator already has `/reports/capital-gains` for spreadsheet-grade output; the correlation matrix is a screen-first analysis. Out of scope.
- **No saved correlation presets.** Saving "BTC + BIST + GOLD over 1M" as a named view is a future enhancement; would need a new `correlation_presets` table. Out of scope. Documented in "Deferred Enhancements".
- **Rollback boundary:** `git revert` of this plan's commits is sufficient — no migration was added so nothing in the schema needs reverting. Match the 29-01 / 28-* precedent of describing the trivial rollback in the SUMMARY.
