<objective>
Decouple the synchronous cross-cutting calls in the portfolio, budget, and bill subsystems by routing them through `ApplicationEventPublisher`. The two named couplings — `InvestmentTransactionService.record(...)` -> `applyToHolding(...)` (transaction commit drives the holding update) and `BillService.pay(...)` -> push/email notification (bill payment drives a user-visible notification) — become event publish sites; new feature-package listeners receive the events with `@TransactionalEventListener(phase = AFTER_COMMIT)`. The third existing inline coupling in scope, `BudgetService.create/update(...)` -> `BudgetRuleService.evaluateForTransaction(...)`, also moves to an event listener so the three coupling shapes ship under one consistent pattern.

Purpose: CONCERNS.md "Domain mutations not audited" was closed in 24-08, but the domain services still own cross-cutting wiring directly: a transaction service mutates holdings, a bill service knows about push subscriptions, and a budget service knows about budget-rule evaluation. The roadmap's Phase 25 line ("Decouple services and de-block the reactive price clients") starts here. After this plan: `InvestmentTransactionService` no longer references `HoldingRepository` from its mutation path, `BillService` no longer references `PushService` / `MailService`, and `BudgetService` no longer references `BudgetRuleService`. Listeners in their own feature packages own the side effects and can fail without rolling back the writer's transaction.

Output: A new `com.fintrack.common.event` package with three plain-record event types (`InvestmentTransactionRecordedEvent`, `InvestmentTransactionDeletedEvent`, `BillPaidEvent`, `BudgetTransactionPersistedEvent`); the four event publishers replace the synchronous calls in `InvestmentTransactionService`, `BillService`, and `BudgetService`; three new `*EventListener` classes (`HoldingProjectionListener` in `portfolio.holding`, `BillPaidNotificationListener` in `bills`, `BudgetRuleEvaluationListener` in `budget`) consume the events with `@TransactionalEventListener(phase = AFTER_COMMIT)`; the `applyToHolding(...)` logic moves to `HoldingProjectionListener` unchanged; the audit emission contract pinned by 24-08 is preserved (the audit row still commits with the writer's transaction, never with the listener); existing `*ServiceTest` and `*ServiceAuditTest` fixtures keep passing because the audit assertions live on the writer side.
</objective>

**Tech stack available:** No new dependencies. `ApplicationEventPublisher` is part of `spring-context`, `@TransactionalEventListener` is part of `spring-tx`, both already on the classpath via `spring-boot-starter`. `@EnableAsync` is already wired in `FinTrackApplication`.

**Established patterns:**
- Audit emission post-write inside the writer service (24-08): `auditService.success(action, userId, currentUsername(), "id=" + entity.getId())` runs AFTER the DB save, BEFORE this plan's event publish.
- Per-service `currentUsername()` static helper reading `SecurityContextHolder.getContext().getAuthentication().getName()`.
- Service ownership of `@Transactional` writes; controllers stay thin.
- `@EventListener(ApplicationReadyEvent.class)` already used in `PriceScheduler` and `SnapshotScheduler` (lifecycle-only, no business events).

**Constraining decisions:**
- 24-08 SUMMARY's "Next Phase Readiness" line explicitly anticipates this plan: "When 25-01 extracts cross-cutting wiring to ApplicationEventPublisher, the audit emission can move to the listener side without changing the entity-id-in-detail contract that's pinned by these tests." We do NOT move the audit emission in this plan — it stays on the writer side. The listener-side audit move (if ever needed) is a separate decision.
- `AuditService.record(...)` runs in `REQUIRES_NEW`. The audit row is committed independently of the writer's transaction, so a failure inside an `AFTER_COMMIT` listener (e.g., push delivery error) leaves the audit row intact and the user-facing transaction committed — exactly the behaviour the listener pattern is meant to enable.
- 23-02 mutation baseline: PortfolioService 85%, HoldingService 85%, InvestmentTransactionService 78%, BudgetService 31%, BillService 70%. After this plan, mutation coverage on the writer services may drop slightly because some mutating logic moves to listeners; the new listener classes pick up dedicated tests so the project-level kill rate (>= 60% gate) is preserved.
- ISS-111 (TagService + AllocationService audit) is independent of this plan and stays open.
- The push delivery path inside `BillReminderScheduler.checkReminders` is system-driven (cron, not user-driven) and does NOT get an event extraction in this plan. Only the user-driven `BillService.pay(...)` -> push notification path is in scope.
- `BudgetRuleService.evaluateForTransaction(...)` is currently called inside `BudgetService.create(...)` and `BudgetService.update(...)` wrapped in `try/catch (Exception e)` — the swallow already exists. Moving it to an `AFTER_COMMIT` listener removes the need for the swallow at the writer site (a listener exception is naturally isolated by Spring).
- The plan explicitly does NOT add `@Async` to the new listeners. `AFTER_COMMIT` semantics are sufficient; async semantics introduce thread-context propagation concerns (SecurityContextHolder, MDC request-id) that are out of scope. If a future plan moves to async, it can opt in per-listener.

**Issues being addressed:** CONCERNS.md "Tech Debt" — synchronous cross-cutting service calls; not a named line item in CONCERNS.md but it is the cleanup target of Phase 25 per ROADMAP.md.
**Concerns being verified:**
- Roadmap Phase 25 "Architecture Cleanup" goal closed end-to-end across plans 25-01, 25-02, 25-03 — this plan owns C1 (cross-cutting events).
