<objective>
Wire Spring Cache + Caffeine across the three hot reads named in Track C2 — asset master list, user settings, and category lookup — and pin explicit invalidation on every write that mutates the cached state. The work has three coupled concerns: (a) install Caffeine as the cache provider so `@EnableCaching` (already on `FinTrackApplication`) routes to an in-process `CaffeineCacheManager` instead of the dead `spring.cache.type: redis` line currently in `application.yml`; (b) introduce the three named caches (`assets`, `userSettings`, `categoryLookup`) with bespoke TTL + size specs; (c) annotate the read methods with `@Cacheable` and the write methods with `@CacheEvict` (or `@CachePut` where the response equals the persisted state) so the cache never serves stale data after a user-driven mutation.

Purpose: Phase 25's roadmap line ("Decouple services and de-block the reactive price clients") closes its second of three sub-plans with this work. 25-01 just landed the `ApplicationEventPublisher` boundary; 25-02 sits cleanly on top — the cache is in-process, so AFTER_COMMIT listeners introduced in 25-01 do not need to invalidate it (a future async/Redis-backed cache would). Concretely after this plan: `GET /api/v1/assets` does not hit the DB unless the asset list is dirty; `GET /api/v1/settings` does not hit the DB unless the per-user settings row is dirty; `GET /api/v1/budget/categories` does not hit the DB unless the per-user category set is dirty. Every owner-facing list page benefits — the asset list and category list are the two queries that load on virtually every page in the dashboard via React Query's default 5-minute staleTime, and the settings call fires on the boundary of every authenticated request that needs the user's currency/locale.

Output: A new `com.fintrack.common.config.CacheConfig` defining a `CaffeineCacheManager` with three named caches and per-cache `Caffeine` specs; a new lightweight `com.fintrack.asset.AssetService` so `@Cacheable` is hit through a Spring proxy boundary (controllers calling repositories directly bypass cache annotations); `@Cacheable` on `AssetService.listAll(...)` and `AssetService.findById(...)`; `@CacheEvict` on the write paths in `TefasFundService.importFund(...)`; `@Cacheable` / `@CacheEvict` on `SettingsService.get(...)`, `update(...)`, `markOnboardingComplete(...)`; `@Cacheable` / `@CacheEvict` on `CategoryService.listAll(...)` and the six category write methods; new tests pinning the cache contract (hit-second-call, evict-after-write); the existing `*ServiceTest` and `*ServiceAuditTest` fixtures keep passing because the `@Cacheable` annotation is invisible to direct unit tests that bypass the Spring proxy. `application.yml`'s `spring.cache.type: redis` line is removed (it had no `@Cacheable` consumers — confirmed by grep) so the new Caffeine config is the single source of truth.
</objective>

**Established patterns:**
- 24-08 audit emission post-write inside the writer service: `auditService.success(action, userId, currentUsername(), "id=" + entity.getId())` runs AFTER the DB save. **Cache eviction must run AFTER the save and before — or alongside — the audit emission so a concurrent reader that sees the new audit row never sees the old cached payload.** Spring's `@CacheEvict` (default `beforeInvocation = false`) fires after the method returns, which is the right ordering: save → audit → method-return → evict.
- 25-01 cross-cutting events run AFTER_COMMIT. Cache invalidation in 25-02 fires synchronously inside the writer's transaction return — this is fine because Caffeine is in-process and Spring's `@CacheEvict` runs after the method body completes, so the evict happens inside the transaction's commit window. The next reader (whose request is serialized after the commit) sees the cache hole and reloads from the DB.
- Per-feature `@Configuration` classes live in `com.fintrack.common.config` (e.g., `CorsProperties.java`, `SecurityConfig.java`, `I18nConfig.java`, `ProductionProfileGuard.java`). The new `CacheConfig` follows that convention.
- Per-service `currentUsername()` helper for audit emission stays untouched.

**Constraining decisions:**
- 25-01-SUMMARY's "Next Phase Readiness" line: "Plan 25-02 (Spring Cache + Caffeine on hot reads) is the next plan. The event boundary established here is the natural place to wire cache invalidation listeners." — In 25-02 we do NOT route invalidation through 25-01's `ApplicationEventPublisher` listeners. Caffeine is in-process; an `@CacheEvict` on the writer method runs inside the writer's call stack, before any listener fires. Listener-based invalidation only matters when the cache is multi-instance (Redis). Documented in Decisions Made. Future plans can revisit if the deployment goes multi-instance.
- 23-02 / 24-08 mutation baseline holds: project kill rate ≥ 60% (currently 64% from 24-08). `@Cacheable` / `@CacheEvict` annotations do not change the method body, so the existing service-level mutation kill rates carry over unchanged.
- AuthService.register(...) creates the initial UserSettings row via `userSettingsRepository.save(settings)` (line 60). The cache is empty at that point (the user has never read settings before). No eviction needed at registration; Spring's cache returns a miss naturally on the first GET. Documented in Decisions Made.
- `AssetController` calls `AssetRepository` directly (no service layer). `@Cacheable` on a JPA repository method does NOT work reliably across Spring Data proxies (the cache proxy and the repository proxy collide; AOP advisor ordering becomes a footgun). Introduce a thin `AssetService` so the `@Cacheable` annotation lives on a `@Service` method called through a clean proxy. The controller switches from injecting `AssetRepository` to injecting `AssetService` for the two listed paths; the upstream price-history paths in the same controller (TEFAS / CoinGecko / Yahoo) are NOT cache targets and stay routed through the existing client beans.

- `SettingsService.update(...)` and `markOnboardingComplete(...)` both return the persisted entity-as-DTO. `@CachePut(value="userSettings", key="#userId")` is the right primitive — it writes the response into the cache so the next reader sees the fresh value without re-querying. The plan uses `@CachePut`, not `@CacheEvict`, for these two methods. `@CacheEvict` would also work but causes a re-read on the next call; `@CachePut` is strictly faster.
- `CategoryService.listAll(...)` returns a `CategoriesResponse` shape (income + expense). The six write methods (`createIncome`, `createExpense`, `updateIncome`, `updateExpense`, `deleteIncome`, `deleteExpense`) each modify exactly one entry in one of the two lists. Returning the new partial response is not the right primitive — there's no write method that returns the full `CategoriesResponse`. Use `@CacheEvict(value="categoryLookup", key="#userId")` on all six. The next read repopulates from DB.

  - `categoryLookup` — per-user, ~20-50 categories total: TTL 30 min, max 16, expire-after-access.

We're switching the **cache** type from `redis` to `caffeine`; `spring-boot-starter-data-redis` (already a dep) continues to back the rate limiter, refresh token store, and login attempts. The two Redis use-sites are not "Spring Cache" consumers — they use `RedisTemplate` directly. Confirmed by grep: no `@Cacheable` ever pointed at Redis.

       package com.fintrack.asset;

       import com.fintrack.asset.dto.AssetResponse;

       import com.fintrack.common.entity.Asset;
       import java.util.List;
       import java.util.Optional;

         }
       }
