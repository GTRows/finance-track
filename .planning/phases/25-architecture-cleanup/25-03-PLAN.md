<objective>
De-block the reactive price clients and the fund-refresh sync path so a long-running external HTTP call no longer holds a JDBC connection or pins a platform thread for its full duration. Two coupled concerns: (a) `PriceSyncService.refreshFunds()` is `@Transactional` and runs a `Thread.sleep(150)` between every TEFAS request — a per-fund DB connection lease for the full ~10-15 s loop that risks pool exhaustion under load; (b) every external price client (`CoinGeckoClient`, `TefasClient`, `ExchangeRateClient`, `YahooFinanceClient`, `PreciousMetalsClient`) calls `Mono.block()` on the WebClient response inside the scheduler thread, so the global `@Scheduled` `refreshLive()` tick serializes the four providers it visits. The fix shrinks the transactional boundary to one short write-only window per fund and runs the upstream HTTP fan-out on Spring Boot 3.2's virtual-thread executor — the `ReceiptOcrWorker` already proves the pattern in this codebase (`Executors.newVirtualThreadPerTaskExecutor()`).

Purpose: Phase 25's roadmap line ("Decouple services and de-block the reactive price clients") closes its third and final sub-plan with this work. 25-01 landed the `ApplicationEventPublisher` boundary; 25-02 landed Spring Cache + Caffeine on the read path. 25-03 closes the open CONCERNS.md entries "Synchronous `WebClient.block()` in price clients" + "`Thread.sleep` inside transactional fund refresh" + (partially) "TEFAS fund refresh latency". After this plan: `refreshFunds()` no longer holds a transaction across `Thread.sleep`; the live tick fans out the four provider calls in parallel rather than sequentially; client-level `block()` happens on a virtual thread that does not pin a platform thread under the JVM's continuation runtime, so the scheduler thread is free during HTTP wait. Owner-facing impact: the 30-second live tick stops drifting toward 15 s of provider serialization; the hourly fund refresh stops parking a JDBC connection for the entire run.

Output: `spring.threads.virtual.enabled=true` in `application.yml` so Spring Boot 3.2 wires Tomcat's request executor and `@Async`/scheduler default executors to virtual threads (preserves existing `@Scheduled` semantics — Spring's `TaskScheduler` adapts when the property is set). A new `priceVirtualExecutor` `ExecutorService` bean in `PriceConfig` (`Executors.newVirtualThreadPerTaskExecutor()`) injected into `PriceSyncService` to fan out fund refreshes and the four-provider live tick. `PriceSyncService.refreshFunds()` rewritten as a two-phase pipeline: phase 1 fans out TEFAS reads on the virtual-thread executor (no `@Transactional`), phase 2 commits the resulting price map in a single short `@Transactional` write window. `PriceSyncService.refreshLive()` rewritten so `refreshCrypto`, `refreshCurrencies`, `refreshMetals`, `refreshStocks` execute their HTTP fetches in parallel via the same executor, with a single `@Transactional` persist at the end. The `Thread.sleep(150)` removed; throttling preserved by capping the executor's parallelism (a `Semaphore`-based gate inside the fan-out, default 4 in-flight, configurable via `price-api.tefas.parallelism`). Existing client `block()` calls stay (they are the safe form once the caller is a virtual thread); the package-private structure of the clients is unchanged. Tests pinned: existing `PriceSyncServiceTest` (20 cases) keeps passing on the new shape with no behavioural drift; new `PriceSyncServiceFundRefreshTest` pins the no-sleep + transaction-shrunk contract with a virtual-thread fixture; new `PriceConfigVirtualExecutorTest` verifies the executor bean is wired and is virtual-thread backed.
</objective>

**Constraining decisions:**
- **Virtual threads vs reactive composition decision.** The CONCERNS.md note lists both. Virtual threads win because: (a) the codebase has no other reactive flow — `WebClient` was always called with `block()`, the controllers are `@RestController` not `@Controller` returning `Mono`, the JPA layer is blocking. Migrating to a Mono-end-to-end shape would require either Spring Data R2DBC (full schema reshuffle) or `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())` everywhere — a much bigger blast radius. (b) `ReceiptOcrWorker` already establishes the virtual-thread pattern, so a second use site is consistent. (c) Spring Boot 3.2's `spring.threads.virtual.enabled` covers Tomcat + `TaskScheduler` + `@Async`, which is the deepest reach we get for one config flag. Reactive composition stays as a deferred option in `Deviations from Plan`.
- **`spring.threads.virtual.enabled=true` impact.** This flag changes the default executor for `@Async` methods (none exist outside `ReceiptOcrWorker` test paths) AND changes the Tomcat request thread pool to virtual threads AND changes Spring's default `TaskScheduler` (used by `@Scheduled`) to `SimpleAsyncTaskScheduler` backed by virtual threads. The third effect matters: every `@Scheduled` method (`PriceScheduler.scheduledRefresh`, `PriceScheduler.scheduledFundRefresh`, `BillReminderScheduler`, `RecurringTemplateScheduler`, `MonthlyReportScheduler`, `SnapshotScheduler`, `AuditRetentionWorker`, `ReceiptOcrWorker`) starts running on a virtual thread instead of the legacy single-threaded `ScheduledThreadPoolExecutor`. This is the desired behaviour; document it explicitly in the SUMMARY. The first-tick semantics are unchanged (cron / fixedDelay still applies).
- **`Thread.sleep` removal vs throttle preservation.** TEFAS is rate-sensitive: a naive 100-fund concurrent fan-out would likely trip rate limiting. Use a `Semaphore(4)` permit inside the fan-out so at most 4 TEFAS requests are in flight at once. Each virtual thread acquires a permit, calls `tefasClient.fetchPrice(...)`, releases; no `Thread.sleep` remains. This is strictly faster than the sequential 150 ms pause (roughly 4× peak throughput on the same upstream) AND no longer holds a transaction across the wait. Configure the parallelism via `price-api.tefas.parallelism` (default 4) so the operator can tune.
- **Transaction boundary shrinkage on `refreshFunds()`.** The current code path holds `@Transactional` across the entire loop — for ~100 funds at 150 ms sleep + ~200 ms HTTP per request, that's roughly 35 seconds with a JDBC connection leased the whole time. New shape:
  1. Phase 1 (no transaction): read the asset list (a `@Transactional(readOnly=true)` helper that returns a list of `(assetId, fundCode, fundType)` tuples and closes immediately), then fan out HTTP calls collecting `Map<UUID, BigDecimal>` of new prices.
  2. Phase 2 (one short transaction): re-load the assets by id batch, write the new prices, save price-history rows. One commit at the end.
  This shrinks the transactional window from ~35 s to ~50 ms (just the writes). Connection pool pressure goes from "1 connection × 35 s" to "1 connection × 50 ms" per refresh.
- **Transaction boundary shrinkage on `refreshLive()`.** Today it's one `@Transactional` method invoking four sequential helpers, each itself `@Transactional`. Spring's transaction propagation default (`REQUIRED`) joins the outer transaction, so the whole thing runs in one ~5-10 s transaction with one JDBC connection. New shape:
  1. Phase 1 (no transaction): four virtual-thread futures fan out the HTTP fetches. The four helpers are renamed `fetchCrypto()`, `fetchCurrencies()`, `fetchMetals()`, `fetchStocks()` and return `List<PriceUpdate>` records (id + new TRY price + optional USD price).
  2. Phase 2 (one short transaction): a `persistUpdates(List<PriceUpdate>)` method takes the four merged lists, re-loads the affected assets, writes prices, saves price-history rows.
  The four `refreshCrypto/Currencies/Metals/Stocks` methods stay public as backward-compatible wrappers that call `fetch*` then `persistUpdates(list)` so the existing test fixtures (which mock the clients and call the per-source methods directly) keep passing without rewrites.
- **Backward-compatible public surface.** `PriceSyncService.refreshAll()`, `refreshLive()`, `refreshCrypto()`, `refreshCurrencies()`, `refreshFunds()`, `refreshMetals()`, `refreshStocks()`, `refreshAsset(UUID)` all keep their signatures and `@Transactional` placement is moved off the per-source methods (now on `persistUpdates` only) but the user-visible return types and counts are unchanged. `PriceController.refresh()` and `PriceScheduler.scheduledRefresh()` are unchanged. Existing `PriceSyncServiceTest` (20 cases) passes without rewrites because it mocks the clients and assets, observes the same writes, and never depended on the `@Transactional` placement.
- **Existing `PriceSyncServiceTest` line 261 typo.** The test file already has a `tefasClient.fetchPrice(eqAny(), eqAny2())` stub at line 261 with helper methods `eqAny()` / `eqAny2()` declared at the bottom — a previous test author worked around Mockito generics. Don't refactor the existing stubs; just verify they still pass on the new shape. Documented in `Deviations from Plan` if any drift surfaces.
- **WebClient `.block()` not removed.** Each client's `block()` call stays. The point of virtual threads is that `block()` on a virtual thread does not pin a platform thread under the JVM's continuation runtime — the carrier thread is freed during the I/O wait. The CONCERNS.md fix-approach line "or move calls to virtual threads" is exactly this: keep the existing client shape, change the caller's thread type. Documented in Decisions Made.
- **`refreshAsset(UUID)` (the per-asset path) stays sequential.** It's a one-shot user-driven endpoint; fanning out a single HTTP call adds executor overhead with zero parallelism benefit. The `@Transactional` boundary on it is small (one asset write + one history row), so it does not exhibit the pool-pressure shape that `refreshFunds()` does. Out of scope for this plan; documented in `Deviations from Plan` -> deferred.
- **TEFAS in-process list cache (`TefasClient.listCache`)** stays as a separate CONCERNS.md entry; this plan does not touch it. Multi-instance moves it to Redis, which is its own work.
- **Per-asset delta WebSocket broadcast** stays a separate CONCERNS.md entry for Phase 30. The plan continues to call `priceBroadcaster.broadcastAll()` after each refresh.
