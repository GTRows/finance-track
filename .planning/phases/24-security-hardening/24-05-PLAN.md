<objective>
Cap audit-log growth and limit PII exposure in audit details by adding a configurable retention scheduler and a redaction utility that runs on every `AuditService.record(...)` call.

Purpose: The `audit_log` table grows monotonically (every login, refresh, password change, TOTP event, and — after plan 24-08 — every domain mutation). Without retention, it bloats Postgres indefinitely. Without PII redaction, the `detail` column can leak email addresses, JWTs, IPs, or recovery codes into a future log dump or backup. The owner-only deployment is not GDPR-bound today, but the audit log is the most likely surface to spill PII into a `pg_dump`.
Output: `AuditPiiRedactor` utility scrubs emails / JWTs / IPv4 / IPv6 / TOTP recovery code patterns from the `detail` field; `AuditService.record(...)` runs every `detail` through the redactor before save and log; `AuditRetentionWorker` `@Scheduled` daily at 03:30 deletes rows older than `fintrack.audit.retention-days` (default 90) in chunks of 1000; `AuditController` exposes `GET /api/v1/admin/audit/retention` returning `{retentionDays, oldestEntry, totalEntries}`; tests for redaction + retention; new audit action `AUDIT_RETENTION_PRUNED`.
</objective>

  <files>backend/src/main/java/com/fintrack/audit/AuditPiiRedactor.java, backend/src/main/java/com/fintrack/audit/AuditService.java, backend/src/test/java/com/fintrack/audit/AuditPiiRedactorTest.java</files>
  <action>
    1. `AuditPiiRedactor` (`@Component`, no state). Single public method `String redact(String detail)`. Compile-once `Pattern` constants for:
       - Email: `[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}` → replace with `[REDACTED:email]`.
       - JWT: `eyJ[A-Za-z0-9_-]+\.eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+` → `[REDACTED:jwt]`.
       - IPv4: `(?<![\d.])(?:\d{1,3}\.){3}\d{1,3}(?![\d.])` → `[REDACTED:ip]`. Use lookarounds to avoid corrupting IDs that contain three dotted segments by accident.
       - IPv6: `(?<![:A-Fa-f0-9])(?:[A-Fa-f0-9]{1,4}:){2,7}[A-Fa-f0-9]{1,4}(?![:A-Fa-f0-9])` → `[REDACTED:ip]`. Anchored to avoid matching arbitrary colon-separated text.
       - TOTP recovery code (project-specific): the recovery codes follow a fixed pattern from `TotpRecoveryCodeService` — read it once before authoring this regex; if codes are e.g. `^[A-Z2-9]{4}-[A-Z2-9]{4}-[A-Z2-9]{4}$` (Crockford-style), match accordingly and redact to `[REDACTED:recovery]`. Add a comment in the redactor referencing the service so a future change to the recovery format is caught at code review.
       - Apply patterns in fixed order; null/blank input returns input unchanged.
    2. `AuditService.record(...)`: inject `AuditPiiRedactor`. Replace the existing `String safeDetail = truncate(detail, DETAIL_MAX);` with `String safeDetail = truncate(redactor.redact(detail), DETAIL_MAX);`. Order matters: redact first so truncation does not slice through a `[REDACTED:...]` token. The MDC log line at the bottom of `record(...)` already prints `safeDetail`; no additional change needed there.
    3. `AuditPiiRedactorTest` — pure unit tests. Cases per pattern: email in plain text, email surrounded by punctuation, JWT in `Bearer eyJ...` context, IPv4 with port suffix, IPv4 inside an URL query string, IPv6 with `::` shorthand, mixed string with two emails + one IPv4, recovery code, null input, blank input, input with no PII (idempotent). Assert each redaction produces the expected literal output. At least 12 cases.
    4. Avoid: do NOT mutate the original `String` reference (Java strings are immutable, but the contract is `redact returns a new string`); do NOT add a "redact whole detail if it looks suspicious" heuristic — false positives become hard to debug; do NOT redact UUIDs (UUIDs already appear in `userId`, no value in scrubbing them from `detail`); do NOT introduce a `RedactionPolicy` interface — premature abstraction; do NOT call `redactor.redact(...)` from controllers or other services — boundary stays at `AuditService.record`.
  </action>

  <action>
    1. `AuditRetentionProperties` — `@ConfigurationProperties(prefix = "fintrack.audit")` record with `int retentionDays` (default 90), `int batchSize` (default 1000), `boolean enabled` (default true). Bind in `application.yml`:
       ```yaml
       fintrack:
         audit:
           retention-days: ${AUDIT_RETENTION_DAYS:90}
           batch-size: ${AUDIT_RETENTION_BATCH_SIZE:1000}
           enabled: ${AUDIT_RETENTION_ENABLED:true}
       ```
    2. `AuditLogRepository` — add: `int deleteByCreatedAtBefore(Instant cutoff)` (Spring Data derived query) AND a custom query for chunked deletion: `@Modifying @Query(value = "DELETE FROM audit_log WHERE id IN (SELECT id FROM audit_log WHERE created_at < :cutoff ORDER BY id LIMIT :limit)", nativeQuery = true) int deleteOldestBatch(@Param("cutoff") Instant cutoff, @Param("limit") int limit);` Native query is correct here because PostgreSQL `DELETE ... LIMIT` is not standard SQL.
    3. `AuditRetentionWorker` in `com.fintrack.scheduler` (`@Component @RequiredArgsConstructor @Slf4j`):
       - `@Scheduled(cron = "0 30 3 * * *")` annotated `prune()` method.
       - Guard: `if (!properties.enabled()) return;`.
       - Compute cutoff: `Instant.now().minus(Duration.ofDays(properties.retentionDays()))`.
       - Loop calling `auditLogRepository.deleteOldestBatch(cutoff, properties.batchSize())` until the returned count is 0 OR the loop has run more than 100 iterations (safety cap to prevent runaway in pathological cases). Sum total deleted.
       - Log `log.info("Audit retention pruned {} rows older than {}", totalDeleted, cutoff);`.
       - Audit `auditService.success(AuditAction.AUDIT_RETENTION_PRUNED, null, "system", String.format("deleted=%d cutoff=%s", totalDeleted, cutoff))`.
       - Wrap each batch call in a small transaction via Spring's default propagation — keep the loop OUTSIDE a single `@Transactional` so individual chunks commit and a slow run does not hold a long lock.
       - Implement `@PostConstruct` `init()` that logs the configured retention at startup (helps verifying env-var binding without needing `/admin/audit/retention`).
    4. Add `AUDIT_RETENTION_PRUNED` to `AuditAction`.
    5. `AuditLogRepositoryDataJpaTest` — extend the existing class from plan 23-01: persist 5 rows with `createdAt` spanning 200 days, call `deleteOldestBatch(now-90days, 100)`, assert only the 3 oldest are gone, the 2 within retention remain. Round-trip the whole loop scenario in a second test (chunk size 2 to exercise the loop).
    6. `AuditRetentionWorkerTest` — Mockito unit test. Mock `AuditLogRepository`, `AuditService`. Cases:
       - Disabled config → `prune()` returns without touching the repository.
       - First batch returns 1000, second returns 1000, third returns 250, fourth returns 0 → totalDeleted = 2250, audit emitted with that count, repository called 4 times.
       - Repository throws → exception bubbles (no swallowing); future runs are not skipped because Spring scheduler retries on cron tick.
    7. Avoid: do NOT use `@Transactional` on the worker method (keep chunk commits separate); do NOT delete in one `DELETE FROM audit_log WHERE created_at < ?` (a single huge delete locks the table; the chunked approach matches the same shape used in operations runbooks); do NOT swallow exceptions in the loop (silent failure is the worst possible outcome here); do NOT make the cron expression configurable (overengineering — env var on `enabled` is the kill switch).
  </action>
