<objective>
Bind every refresh token to a SHA-256 fingerprint of (user-agent + IP /24 prefix) so a leaked refresh token from one device cannot be used from another.

Purpose: Refresh tokens already record `user_agent` and `ip_address` for the active-sessions UI, but those values are advisory only — they are not used as a gate on `/auth/refresh`. A token exfiltrated via XSS (the residual risk flagged in PROJECT key decisions) becomes useless to an attacker on a different network or browser the moment we make the fingerprint a hard validation condition.
Output: Flyway V39 adds `fingerprint CHAR(64)` to `refresh_tokens`; `RefreshTokenFingerprintService.compute(userAgent, ip)` produces a hex SHA-256 of UA + IP-prefix; `RefreshTokenService.validate(...)` accepts the current request's UA+IP and rejects mismatches with `REFRESH_FINGERPRINT_MISMATCH`; rotation rebinds to the current fingerprint; legacy NULL fingerprints are bound on first refresh (one-shot grace); audit trail captures every mismatch.
</objective>

  <action>
    1. `V39__add_refresh_token_fingerprint.sql`: `ALTER TABLE refresh_tokens ADD COLUMN fingerprint CHAR(64);` — nullable so existing rows survive (one-shot grace handled in code).
    2. `RefreshToken` entity: add `@Column(name = "fingerprint", length = 64) private String fingerprint;` (nullable). Existing fields untouched.
    3. `RefreshTokenFingerprintService` (`@Service`, no state):
       - `String compute(String userAgent, String ipAddress)`. Normalize: `ua = userAgent == null ? "" : userAgent.trim()`. Compute IP prefix:
         - Null/blank → `""`.
         - IPv4 (matches `^(\d{1,3}\.){3}\d{1,3}$`) → drop the last octet (`a.b.c.0/24`).
         - IPv6 → keep the first three groups + `::/48` (e.g., `2001:db8:abcd::/48`).
         - Anything else (X-Forwarded-For with multiple commas already handled by RequestContext) → use as-is after `.trim()`.
       - Concatenate `prefix + "|" + ua` (delimiter chosen to avoid the IP/UA boundary collision).
       - SHA-256 via `MessageDigest.getInstance("SHA-256")`, hex-lower-case, return.
       - Pure function; deterministic; no DB.
    4. `RefreshTokenService.createRefreshToken(UUID userId, String userAgent, String ipAddress)`: compute fingerprint via the new service and persist on the new row.
    5. `RefreshTokenService.validate(String token)` becomes `validate(String token, String currentUserAgent, String currentIp)`:
       - Existing not-found / expired branches unchanged.
       - If `entity.getFingerprint() == null`: legacy row, treat as one-shot grace — compute current fingerprint, bind it to the row (`entity.setFingerprint(...)`, save), do NOT reject. Audit `REFRESH_FINGERPRINT_BOUND` (new action) success with detail "legacy upgrade".
       - If `entity.getFingerprint() != null`: compute current fingerprint; on mismatch, delete the entity, audit `REFRESH_FINGERPRINT_MISMATCH` failure with detail = stored fingerprint prefix `(stored=AAAA…, current=BBBB…)` (only first 8 chars to avoid logging the full secret material), throw `BusinessRuleException("Session fingerprint mismatch", "REFRESH_FINGERPRINT_MISMATCH")`.
    6. `RefreshTokenService.rotate(...)` already calls `createRefreshToken(...)` after `deleteByToken(...)` — the new fingerprint is computed from the current request automatically. No change required beyond what Task 1 wiring provides.
    7. `AuthService.refresh(RefreshRequest request)`: change the `validate(request.refreshToken())` call site to `validate(request.refreshToken(), RequestContext.userAgent(), RequestContext.clientIp())`. Same change at any other call site of `validate(...)` (search via `Grep("refreshTokenService\\.validate\\(", "backend/src")` — there should be exactly one).
    8. `AuditAction`: add `REFRESH_FINGERPRINT_BOUND`, `REFRESH_FINGERPRINT_MISMATCH`.
    9. Avoid: do NOT log the full fingerprint in any audit detail (it is a stable identifier of the session, treat it as sensitive); do NOT add the legacy-grace logic to rotation (rotation re-binds anyway via `createRefreshToken`); do NOT change the API surface (`validate` is a service method, not exposed); do NOT short-circuit on null IP/UA — the deterministic empty-string normalisation means clients without those headers all share the same fingerprint, which is a tradeoff (acceptable: a token from a non-browser client is still bound to the empty-string fingerprint and will reject when re-used from a browser); do NOT make this configurable (a feature flag here is silent disablement and that defeats the security goal).
  </action>
