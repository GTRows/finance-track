<objective>
Complete the WebAuthn passkey flow: backend assertion (login) ceremony, list+revoke endpoints, and the frontend `navigator.credentials.create` / `navigator.credentials.get` integration so a user can enrol a passkey from the profile page and sign in with it from the login page.

Purpose: Plan 24-02 stopped at backend registration. Without assertion + UI, no user can actually use passkeys. This plan closes the loop end-to-end and makes passkeys an alternative sign-in alongside the existing username/password + TOTP path.
Output: `WebAuthnAssertionService.start(username)` (returns challenge + allowed credentials), `WebAuthnAssertionService.finish(body)` (verifies signature, returns `AuthResponse`); `WebAuthnAssertionController` with public `/login/start` + `/login/finish`; `AuthenticatorController` with authenticated `GET /api/v1/auth/webauthn/authenticators` (list) and `DELETE /{id}` (revoke); frontend `webauthn.api.ts`, `useWebAuthnRegister`, `useWebAuthnLogin` hooks, `WebAuthnRegisterButton` on profile page, `WebAuthnLoginButton` on login page; e2e-style backend tests; OpenAPI regen.
</objective>

  <action>
    1. `WebAuthnAssertionService` (`@Service @RequiredArgsConstructor`). Inject `UserRepository`, `AuthenticatorRepository`, `WebAuthnProperties`, `WebAuthnManager` (or yubico equivalent), `StringRedisTemplate`, `RefreshTokenService`, `JwtUtil`, `AuditService`. Methods:
       - `AssertionStartResponse start(String username)` — load user; if not found, return a generic challenge-only response (do not leak account existence) but still write a placeholder Redis entry to keep timing consistent; if found, list `Authenticator` rows for the user, build `allowCredentials` (id base64url-encoded + transports), generate a 32-byte challenge, store in Redis under key `webauthn:assert:<base64url(challenge)>` with 5-min TTL bound to the userId, return `(challenge, rpId, timeout=60_000, allowCredentials, userVerification="preferred")`. The Redis VALUE is the userId so finish() can resolve who is signing in without trusting client-supplied identity.
       - `AuthResponse finish(AssertionFinishRequest body)` — pop the Redis entry by challenge (atomic getAndDelete), parse the userId, load `User`, find the `Authenticator` by `body.credentialId`, run the chosen library's verifier with (rpId, origin, challenge, body.clientDataJSON, body.authenticatorData, body.signature, public_key_cose, sign_count). On success: persist new `sign_count` and `last_used_at = now()`; if the new sign_count is NOT strictly greater than the stored one, treat as cloned credential — revoke the authenticator (delete row), audit `WEBAUTHN_CLONE_DETECTED`, throw `BusinessRuleException("Authenticator integrity check failed", "WEBAUTHN_CLONE_DETECTED")`. On valid: build `AuthResponse` exactly like `AuthService.buildAuthResponse(user)` (issue access JWT + refresh token via `RefreshTokenService.createRefreshToken(user.getId(), RequestContext.userAgent(), RequestContext.clientIp())`); audit `WEBAUTHN_LOGIN`; if `user.isTotpEnabled()`, issue a TOTP challenge token instead of a full session (mirrors password-login behaviour) — passkeys do NOT bypass the TOTP gate; users who choose to disable TOTP after enrolling a passkey can do so via the existing flow.
       - All write methods `@Transactional`. Read-only `start` is `@Transactional(readOnly = true)`.
    2. `WebAuthnAssertionController` — `@RestController @RequestMapping("/api/v1/auth/webauthn/login")`. Public endpoints (added to `PUBLIC_PATHS` in `SecurityConfig`): `POST /start` accepting `AssertionStartRequest(@NotBlank String username)`, `POST /finish` accepting `AssertionFinishRequest(@NotBlank String credentialId, @NotBlank String clientDataJSON, @NotBlank String authenticatorData, @NotBlank String signature, String userHandle)`.
    3. `AuthenticatorController` — `@RestController @RequestMapping("/api/v1/auth/webauthn/authenticators")`. Authenticated. `GET /` → `List<AuthenticatorResponse(UUID id, String name, Instant createdAt, Instant lastUsedAt, String transports)>` filtered by `userId`; `DELETE /{id}` → 204; both use `findByIdAndUserId` / `deleteByIdAndUserId`. Audit `WEBAUTHN_AUTHENTICATOR_REVOKED` on delete with the `id` in the detail.
    4. `SecurityConfig.PUBLIC_PATHS` — append `/api/v1/auth/webauthn/login/start`, `/api/v1/auth/webauthn/login/finish`. Keep `/api/v1/auth/webauthn/register/**` and `/api/v1/auth/webauthn/authenticators/**` authenticated.
    5. `AuditAction` — add `WEBAUTHN_LOGIN`, `WEBAUTHN_LOGIN_FAILED`, `WEBAUTHN_CLONE_DETECTED`, `WEBAUTHN_AUTHENTICATOR_REVOKED`.
    6. Tests:
       - `WebAuthnAssertionServiceTest` (`@ExtendWith(MockitoExtension.class)`). Cases: (a) `start` with known username writes Redis entry and returns options with allowCredentials; (b) `start` with unknown username returns a generic challenge but does NOT write Redis (or writes a decoy entry — pick decoy and assert the value is not a real userId); (c) `finish` happy path verifies signature, returns AuthResponse with non-null accessToken and refreshToken, advances sign_count, audits WEBAUTHN_LOGIN; (d) `finish` with sign_count NOT strictly greater triggers clone-detection branch, deletes the authenticator, audits WEBAUTHN_CLONE_DETECTED, throws; (e) `finish` with TOTP-enabled user returns the challenge response shape (no refresh token, with `challengeToken` set), audits TOTP_CHALLENGE_ISSUED.
       - `AuthenticatorControllerWebMvcTest` (`@WebMvcTest(AuthenticatorController.class)` with `@Import` for any required config) — list returns only the user's rows; delete returns 204 and audits.
    7. Avoid: do NOT issue a session before signature verification; do NOT trust the client-supplied `userHandle` for identity (use the Redis-stored userId); do NOT silently allow sign_count == previous value (anti-clone is the whole point of sign_count); do NOT mark the assertion endpoints as authenticated (they are the login flow); do NOT skip the TOTP branch — passkeys are an authenticator factor, not an MFA replacement when TOTP is on.
