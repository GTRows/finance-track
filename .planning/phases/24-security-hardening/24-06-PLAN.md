<objective>
Replace the auth-header-only receipt download path with a short-lived HMAC-signed URL so the budget UI can render receipt images directly via `<img src>` without smuggling JWTs through query strings.

Purpose: The current `GET /api/v1/budget/transactions/{id}/receipt` endpoint requires a `Bearer` token in the `Authorization` header. Browsers cannot send headers from `<img src>`, which today forces the UI to fetch as a Blob and convert to an object URL (ugly, slow, and breaks the OCR-text reveal panel that wants a thumbnail). A 5-minute HMAC-signed URL solves the rendering problem without weakening auth, since the signature is owner-bound and time-bound.
Output: `ReceiptUrlSigner` service with `sign(userId, txnId, ttl)` returning a base64url token and `verify(userId, txnId, token)` returning bool; a new authenticated `GET /api/v1/budget/transactions/{id}/receipt/url` returning `{url, expiresAt}`; the existing receipt-download endpoint accepts `?token=` as an alternative to JWT and skips the security filter only when the token is present and valid; HMAC secret comes from `RECEIPT_SIGNING_SECRET` env var (production-fail-fast in plan 24-07); frontend `useReceiptUrl(txnId)` hook + `<ReceiptThumbnail>` rendering component using the signed URL.
</objective>

  <files>backend/src/main/java/com/fintrack/budget/receipt/ReceiptUrlSigner.java, backend/src/main/java/com/fintrack/budget/receipt/ReceiptSigningProperties.java, backend/src/main/resources/application.yml, backend/src/test/java/com/fintrack/budget/receipt/ReceiptUrlSignerTest.java</files>
  <action>
    1. `ReceiptSigningProperties` — `@ConfigurationProperties(prefix = "fintrack.receipt")` record with `String signingSecret` and `Duration tokenTtl` (default `PT5M`). Bind in `application.yml` under existing `fintrack:` block:
       ```yaml
       fintrack:
         receipt:
           signing-secret: ${RECEIPT_SIGNING_SECRET:dev-receipt-signing-secret-change-in-production-must-be-32-bytes}
           token-ttl: ${RECEIPT_TOKEN_TTL:PT5M}
       ```
       Production profile fail-fast for blank secret is added in plan 24-07; for now the dev default keeps local boots working. The development profile already sets `JWT_SECRET` defaults the same way.
    2. `ReceiptUrlSigner` (`@Service @RequiredArgsConstructor`):
       - `String sign(UUID userId, UUID txnId)` — compute `expiresAtEpochSec = now().plus(properties.tokenTtl()).getEpochSecond()`, build canonical string `userId + "|" + txnId + "|" + expiresAtEpochSec`, HMAC-SHA256 with the configured secret as key, base64url-encode the (mac || expiresAtEpochSec) payload as a single token: `base64url(expiresAtEpochSec ":" hexMac)` — keep human-debuggable but tamper-evident. The token MUST encode the expiry inline; the verifier cannot trust an externally-supplied expiry.
       - `boolean verify(UUID userId, UUID txnId, String token)` — base64url-decode, split on `:`, parse expiry, check `Instant.ofEpochSecond(expiry).isAfter(now())`, recompute HMAC over `userId|txnId|expiry`, constant-time compare with `MessageDigest.isEqual(...)`. Any failure → `false`. No exceptions surface.
       - `Mac` instance is created per call (HMAC-SHA256 init from a `SecretKeySpec` of the UTF-8 bytes of the secret). At init in `@PostConstruct`, validate the secret is at least 32 bytes; throw `IllegalStateException` if shorter (the dev default is exactly 32 bytes by design — plan 24-07 hardens this further in production).
    3. `ReceiptUrlSignerTest` — pure unit. Cases: (a) `verify(sign(...))` returns true on valid token; (b) `verify` returns false on tampered token (last char flipped); (c) `verify` returns false on wrong userId; (d) `verify` returns false on wrong txnId; (e) `verify` returns false on expired token (advance the clock — inject a `Clock` if needed, or use `Thread.sleep` for a 1-second TTL test); (f) constructor throws when secret is shorter than 32 bytes; (g) sign returns the same length string for the same inputs (sanity).
    4. Avoid: do NOT use plain string `equals` for the MAC compare (timing attack); do NOT include the secret material in any log line, ever; do NOT use the JWT signing secret for receipt URLs (different concern, different rotation cadence); do NOT make the token storage-backed (the whole point is statelessness — the validator never touches the DB).
  </action>

  </verify>
  <done>
    Signer is pure, deterministic, and tamper-evident; secret-length guard fires; tests cover positive, tamper, expiry, and wrong-target paths.

    2. `ReceiptController` — add `@GetMapping("/url")` (auth required) returning `ReceiptUrlResponse`. Construct the URL as `${baseUrl}/api/v1/budget/transactions/{id}/receipt?token=${signed}`. Read base URL from `fintrack.mail.base-url` (already exists; reuse) — produces a fully-qualified URL safe for `<img src>` regardless of how the SPA is served. Return `expiresAt = now + properties.tokenTtl()`.
    3. Modify the existing `download(...)` handler to accept an optional `@RequestParam(required = false) String token` AND remove the `@AuthenticationPrincipal` requirement when the token is present. Implementation: keep the controller method signature with `@AuthenticationPrincipal FinTrackUserDetails user` AND `@RequestParam(required = false) String token`, but extract the userId via:
       - if `user != null` → `userId = user.getId()`
       - else if `token != null` → resolve userId from the signed token: this requires the token to encode the userId. Since the signer already signs `userId|txnId|expiry`, the URL needs to include the userId implicitly via the verifier. Cleaner approach: the URL carries `?token=` and the controller passes (txnId from path, token from query) to a new `ReceiptStorageService.loadBySignedToken(txnId, token)` method that internally decodes the userId from the token and calls the existing `load(userId, txnId)`. Implement this loadBySignedToken to call `ReceiptUrlSigner.verifyAndExtractUserId(...)` (additional helper on the signer).
       - Add `String verifyAndExtractUserId(UUID txnId, String token)` to `ReceiptUrlSigner`: returns the userId encoded in the token if signature + expiry valid; throws `BusinessRuleException("Invalid signed URL", "RECEIPT_TOKEN_INVALID")` otherwise.
    4. `SecurityConfig` — add a new public path matcher for `GET /api/v1/budget/transactions/*/receipt` with the constraint that it requires a `?token=` query parameter. Easiest implementation: `SignedReceiptTokenFilter` `@Component extends OncePerRequestFilter` placed BEFORE `JwtAuthFilter`. The filter only acts when the request URI matches `^/api/v1/budget/transactions/[^/]+/receipt$` AND `request.getMethod().equals("GET")` AND `request.getParameter("token") != null`. In that case it sets a synthetic anonymous-but-permitted authentication on `SecurityContextHolder` so the existing security chain treats the request as authorized; the controller then performs the actual signature check via `ReceiptUrlSigner.verifyAndExtractUserId` and throws on failure. This keeps the global `anyRequest().authenticated()` rule intact and pushes the cryptographic gate into the controller boundary where token validation already lives.
    5. `ReceiptControllerWebMvcTest` — `@WebMvcTest(ReceiptController.class)` cases: (a) `GET /receipt/url` with auth returns a non-blank URL and a non-null expiresAt; (b) `GET /receipt?token=valid` returns 200 with the file bytes and the right `Content-Type`; (c) `GET /receipt?token=tampered` returns 400 with code `RECEIPT_TOKEN_INVALID`; (d) `GET /receipt?token=expired` returns 400 (use a `Clock` or override `properties.tokenTtl()` to a negative duration in a slice config); (e) `GET /receipt` without auth and without token still returns 401 (existing behaviour preserved); (f) `GET /receipt` with valid JWT and no token still returns 200 (existing behaviour preserved).
    6. Avoid: do NOT add the receipt path to `PUBLIC_PATHS` unconditionally (a missing `?token` would expose the receipt to anyone); do NOT validate the token inside the security filter (the filter scaffolds; the controller boundary makes the cryptographic call so the same logic exercises both signature+expiry tests); do NOT include the userId in the URL path (`/users/{userId}/receipts/...`) — the token is the source of truth for ownership and exposing userIds in URLs leaks identity; do NOT increase the TTL above 5 minutes by default (`<img src>` re-fetches are cheap; long TTLs reduce the rotation safety margin); do NOT cache the URL in the frontend store (Task 3 is a per-render React Query call with `staleTime: 4*60*1000`).
  </action>
